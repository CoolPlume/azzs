### 1.1 夜间敌对复核新增缺口（04:04）

安全审计按 Graphify 先定位、再回读正式规格、研究、事项和维护指南；没有联网，也没有把推荐方案写成已确认行为。新增事实如下：

- **安装版作用域仍未闭合**：正式规格只冻结便携版/安装版和运行期 UAC；研究中“per-machine + UAC”只是非决定性的样机建议。`per-machine`、`per-user`、dual-purpose、ARP/升级/卸载、ProgramData ACL 与第二 Windows 用户可见性仍需产品决定和实机证据。
- **第三方 EULA、隐私条款和可选推广同意没有形成合同**：现有 `SW-24..30` 约束静默方式、结果检测和搜狗的两项安装偏好，但没有定义工作台能否代用户接受条款、条款/推广版本记录、无法识别条款时的回退或审计字段。再分发许可台账不能替代终端用户同意。
- **应用自更新的 Release 通道未定义**：`UPD-01..07` 和 ADR-0006 只描述手动/一键动作与失败回退；没有 stable 与 draft/prerelease/nightly 过滤、Release/tag/asset 选择、版本比较、降级和架构/发行形态配对规则。软件目录的 `latest_stable` 不能外推为应用更新合同。
- **高权限公开项目缺安全报告入口和支持版本政策**：根目录没有 `SECURITY.md`、`SUPPORT.md` 或私密报告入口；事项 30 只覆盖公开仓库基线，CONTRIBUTING 将公开 Issue 作为反馈入口。当前也没有“首个 Release 后哪些版本继续收安全修复”的政策。
- **P0 范围风险**：Q4a-b 尚未回答，ADR-0006/事项 17 仍允许未闭合真实性的更新链进入实现队列；事项 28 的紧急撤回仅覆盖软件优化，软件来源、安装档案、系统设置、其他受控能力和工作台版本没有同等级安全阻止通道。

这些是实现前要补齐的事实/决策登记，不是对维护者的代答。最小闭环分别是：冻结安装作用域并覆盖双用户与生命周期；建立第三方安装器 consent/offer 档案和交互式回退；在 Q4a 后冻结应用 Release 通道与版本比较；公开源码前加入私密漏洞报告政策，首个 Release 前决定 latest 或 N/N-1 支持窗口；在 Q4g-h 中明确跨类别安全阻止的唯一 owner。

### 1.2 第三次前沿审计新增缺口（04:20）

以下四项是已有规格片段的组合缺口，不是简单补充 UI 文案：

- **手动导入目录的支持边界与信任模型（Q16，P0/P1）**：`CAT-21/22` 允许用户确认来源无法验证的目录并使其成为当前有效目录，但“普通使用模式不正式支持自制目录包”与高级视图导入能力同时存在。需要决定普通用户是否能导入任意未签名目录、工作台承担何种支持责任、如何记录来源/权限/回退，以及是否只允许显式调试模式。
- **第三方安装器的重启及后置副作用合同（Q17，P1；首版必达软件为 P0）**：批次只等待首进程退出并按结果检测，`install_profile` 没有统一的重启、子进程、服务、驱动和完成信号合同。需要定义未知后置行为的暂停/确认状态、重启后验证、关闭工作台后的进程绑定和是否阻止下一项。
- **目录模式安全字段的向前兼容规则（Q18，P1）**：未知字段可忽略、未知模式版本拒绝，但没有区分显示扩展与改变来源真实性、用户同意、执行能力或紧急阻止语义的安全字段。需要为安全能力声明最低工作台版本/模式代次，旧工作台遇到未知安全能力时失败关闭。
- **应用更新健康检查与回退触发条件（Q19，P0）**：`UPD-04` 和事项 17 只写下载、替换或新版启动失败；没有定义状态迁移失败、启动后崩溃、健康超时、活动批次占用、回退失败和“安装事务成功但应用更新失败”的分层结果。

敌对复核还把 Q17/Q19 下的批次占用释放、结果检测器无副作用、更新与活动任务互斥、重启屏障一次性启动注册清理、来源手动交接并发、驱动助手安装合同列为六个 P1 子合同；它们不另起无 owner 的根问题，但必须进入相应事项的负向验收。

具体证据、依赖和明日四题回复格式见[新增前沿审计](new-frontier-audit-2026-08-10.md)。

## 2. 决策树与当前前沿

当前任务第一轮只包含没有未决前置答案的 Q2、Q3、Q4a-b、Q5a-e、Q6、Q8、Q9、Q10、Q11a-b 与 Q12-Q15。Q1 由另一个 `grill-with-docs` 任务单独提问；Q16-Q19 是新增的后续前沿，分别依赖目录模式/调试边界、安装档案与重启恢复、安全模式版本和 Q4a/Q5 状态合同。Q4c-h、Q5f-l、Q7、`REDIST-D2..D10`、`RELEASE-D2..D7`、`INSTALLER-D3/D6-D8/D10-D12/D14` 也都有未决前置或工程事实，不能与根问题混成同一轮。事实调查已经完成的分支也不会因此被当成产品答案。

### 当前任务第一轮

❓ **Q2 - 救援伴随工具的质量责任**：断网救援版和超大离线版是否继续携带两个由工作台启动、但不由本项目实现或测试的独立 EXE？常驻管理员工作台启动它们时，可能与“所有提权执行能力都随工作台构建并通过同一检查”的既有架构边界冲突。

➡️ 建议只在它们成为有源码、版本、可复现构建、许可、完整性、最小冒烟测试和明确进程令牌合同的项目受控制品后随包；否则只提供外部交接，不随包、不从提权进程直接启动。

❓ **Q3 - U 盘厂商网卡驱动的边界**：“从 U 盘导入厂商网卡驱动”是只打开位置并让用户/厂商安装器接管，还是由工作台选择、验证并安装 INF/EXE？后者会推翻 ADR-0009 的“工作台不匹配、下载或安装具体驱动包”。

➡️ 建议首版保持外部交接：工作台说明、定位和记录流程，但不选择或安装具体驱动包；若确需自动安装，应另立安全模型并以新 ADR 明确取代原边界。

❓ **Q4a-b - 两条执行链是否必须有真实性根**：一键自更新和第三方安装器自动管理员执行是两条不同链。是否仍允许它们在没有项目签名、独立摘要或预期发布者政策时自动取得并执行字节？风险披露不能阻止被替换的二进制继承父进程管理员令牌。

➡️ 建议：**Q4a** 没有代码签名、受信分发平台或独立带外首次信任根时取消一键替换，只保留外部手动下载；只把更新公钥嵌进未签名应用不能证明首次项目身份。**Q4b** 自动管理员执行默认要求受信签名且发布者符合该软件预期，无签名且无独立认证摘要时只作外部交接。两项可整体接受或分别修改；控制元数据、紧急阻止、HTTP、离线吊销、外置缓存和进程权限边界在下一轮按依赖展开。

❓ **Q5 - 持久化与 Windows 用户合同**：便携版和安装版共享“设备级状态”已经确认，但“设备级”尚未定义状态主体、权威介质、应用版本兼容窗口、共享缓存并发范围和未保存检查点的最大丢失窗口。尤其是标准用户输入另一名管理员凭据时，进程令牌用户不再等于交互用户；HKCU 和用户配置文件原值不能跨用户共用一份无主体记录。

➡️ 建议把 Q5 作为一个可整体接受或逐项修改的决策包：**Q5a** 首版只支持登录用户用自己的拆分管理员令牌提权；**Q5b** 权威状态只放本机 `ProgramData`，网络/移动位置只承载软件包缓存；**Q5c** 只保证发布链 N 与 N-1，未知新模式拒绝写入；**Q5d** 共享缓存首版只保证同机多实例，不保证多台电脑同时写同一 SMB 位置；**Q5e** 未保存修改最多丢失 10 秒，并在应用失活和高风险操作前强制检查点。用户级记录按状态主体 SID 隔离并使用明确 ACL。各项尚未确认。

❓ **Q6 - 当前状态与操作结果是否分层**：`CONTEXT.md` 把“已安装”限定为执行前检测，规格又用“已完成”表示用户确认或执行结果，却没有工作台安装并验证成功后的规范名称。是否分别建模“软件当前状态”和“本次安装操作结果”？

➡️ 建议分层。当前状态使用“已安装／未安装／无法确认”等；操作结果使用“安装成功／安装失败／结果待确认／已跳过”等。界面可以按上下文显示短词，但核心、历史和日志不能共用一个含义模糊的枚举。

❓ **Q8 - 无真实 Windows 证据能否发布**：当前事项允许在没有真实 Windows、ARM64、Win10 22H2 或搜狗环境验证时发布，只在开发者证据中标记“未实机验证”。是否维持这一发布政策？

➡️ 建议允许生成开发构建，但首个公开 Release 至少要求 Windows 11 x64 主流程、Win10 22H2 冒烟、ARM64 启动/架构回退和搜狗首版必达路径的真实证据；无法取得的矩阵项可以明确标记，而不是让所有实机证据都非阻断。

❓ **Q9 - 超大离线版是否服从权利与身份门禁**：候选稿中的部分商业软件没有公开再分发授权，另有资源连唯一上游身份都未闭合。超大离线版是必须等所有候选都能携带才可发布，还是允许排除未通过对象并只承诺“当前已取得权利且证据通过的最大离线集合”？

➡️ 建议采用后者。候选库存不是发行承诺；未知许可、`NOASSERTION`、身份未闭合或非 `accepted` 的资产一律不进入公开制品，不能由普通 exception 放行。该答案合并关闭 `REDIST-D1`、`REDIST-D7` 与 `REDIST-D11` 的根政策，精确软件取舍留到后续分支。

❓ **Q10 - 不签名是否仍允许完整性与来源证明**：ADR-0005 与 `SEC-05` 要求不提供 SHA-256 或源码提交关联，但 GitHub Release API 已显示 asset digest，immutable release 和 build attestation 也会关联 tag、commit 与工作流。是否把“不做 Windows 代码签名”与“提供摘要／provenance”分开？

➡️ 建议分开并显式 supersede 旧措辞：可以继续不做 Authenticode 签名，但公开每个最终资产的 SHA-256、source commit、build/SBOM attestation 和可长期复核的证据。若继续全面禁止摘要与源码关联，就必须同时放弃这些验证能力，不能在验收中暗用。

❓ **Q11a - ARM64 安装资产是否要求安装器进程也原生**：当前“x64 与 ARM64 安装版”只明确了工作台负载架构。是否还要求 installer/bootstrapper、uninstaller、插件和必要自定义动作都原生 ARM64，还是允许 ARM64 用户通过系统的 x86/x64 模拟运行安装器？

➡️ 建议凡以“ARM64 安装版”命名的资产都要求安装链关键进程原生 ARM64；否则必须准确改称“通过模拟安装 ARM64 原生工作台”，并保留对应 Win10/Win11 on Arm 实机限制。该答案映射 `INSTALLER-D1`。

❓ **Q11b - 安装版是否承诺标准 Repair**：安装版是否要求在 Windows 应用管理入口提供标准 Repair，用于恢复该版本安装器拥有的缺失／旧程序文件？这不会修复或重置 ProgramData 中的动态状态，也不等于面向企业受管部署。

➡️ 建议要求标准 Repair，但严格限定为安装器拥有的程序文件和声明资源；设备状态、缓存、日志、草稿和恢复记录不属于 Repair 对象。该答案映射 `INSTALLER-D2`，并把脚本式安装器需要自建 repair 的成本显式纳入淘汰门槛。

❓ **Q12 - WiX 7 官方二进制工具条款**：如果保留 WiX 7 候选，项目是否接受官方 Binary Release 的 OSMF EULA；若不接受，是否愿意长期维护基于 MS-RL 源码自行构建的工具链？已另付支持费只豁免 Fee，不豁免 EULA 本身。

➡️ 建议按项目实际用途书面记录条款适用性，不默认自己豁免。若既不接受官方 Binary Release 条款，也不愿承担源码自编、更新和可复现性维护，立即淘汰 WiX 候选。该题映射 `INSTALLER-D4`，研究记录不构成法律意见。

❓ **Q13 - 普通卸载是否只删除程序文件**：在完整数据分类和“删除本机数据”用例尚未冻结前，普通卸载是否保留 ProgramData 中全部状态、历史、目录、草稿、检查点、偏好、缓存和日志，只移除可由安装资产重建的程序文件与登记？

➡️ 建议是。显式删除本机数据另作受保护用例并等待 Q5 后续分类；安装器不得递归猜删稳定设备根。该题映射 `INSTALLER-D5`，并成为后续 `D6/D7` 的前置。

❓ **Q14 - 安装器可重复构建承诺到哪一级**：首版只要求精确版本、锁定输入、在固定 builder 上稳定成功且两次输出差异可解释，还是立即要求跨干净 builder 的 bit-for-bit 相同？

➡️ 建议首版采用前者作为 P0，同时保留摘要和差异报告；只有确有供应链或审计需求时，再把时间戳、压缩、GUID、绝对路径和 builder 镜像全部纳入 bit-for-bit 门禁。该题映射 `INSTALLER-D9`。

❓ **Q15 - ARM64 设备上既有 x64 安装版如何迁移**：ARM64 首次安装是否拒绝 x64 资产；若已经安装 x64 版，原生 ARM64 安装版应阻止、受控替换还是允许并存？

➡️ 建议首次安装使用原生 ARM64 资产；既有 x64 安装采用互斥的受控迁移，保留共享设备状态并清理旧程序文件和登记。不得默认让两种架构安装版并存后共同读写同一状态根。该题映射 `INSTALLER-D13`。

## 8. 工具链一手资料结论

截至 2026-08-10，可用于最小样机的稳定候选是 Windows App SDK/WinUI 3 2.3.1、Visual Studio 2026 18.8.2、MSVC 14.50/19.50 和 Windows SDK 10.0.28000.2526。它们都必须锁精确版本并记录本机安装布局；“Stable”不证明本项目在 Windows 10 22H2、x64/ARM64、自包含与未签名发行组合上已经通过。

开始产品代码前有五个工具链缺口：

1. MSVC 没有 `/std:c++26`；`/std:c++latest` 会同时打开进行中或实验能力。现有“C++26 目标”和“不依赖实验能力”不能同时按字面满足。建议维护者确认产品口径，工程上再以固定编译器和特性允许清单限制实际使用面。
2. `WindowsAppSDKSelfContained=true` 只证明 Windows App SDK 依赖可随应用部署，不能证明 VC Runtime 已闭合。需要在无 Visual Studio、无 Windows App SDK、无预装 VC Runtime 的干净机上比较 `/MT`、app-local VC Runtime 与安装版捆绑 Redistributable。
3. 优先验证“MSBuild 管 WinUI 3/XAML 宿主，CMake/CTest 管可移植核心”的候选布局；这是架构契合度最高的工程假设，但必须证明只有一个最终装配入口、两套构建不会产生不同宏/ABI 语义。
4. 长期不签名与正式 MSIX 分发冲突。Windows 11 的 unsigned MSIX 是管理员 PowerShell 测试例外，不适用于广泛分发，也覆盖不了 Windows 10 22H2；若 ADR-0005 不变，候选只能是 unpackaged 自包含便携 ZIP 加传统未签名安装器。
5. Windows 10 22H2 在技术最低版本范围内，但已于 2025-10-14 结束常规支持。项目可以称其为“最低设计目标”，不能声称该组合仍获微软完整支持；ARM64 旧系统环境不可得时必须保留未验证证据缺口。

版本锁定前的 P0 样机只验证工具链和部署，不实现产品功能：最小 C++/WinRT + XAML 的 x64/ARM64、Debug/Release、自包含构建；`/std:c++latest` 与生成代码兼容性；MSBuild/CMake 所有权；干净机 CRT 闭合；断网启动与制品依赖扫描。样机结果再决定版本锁、构建入口、CRT 和传统安装器技术。

安装器同负载样机的非决定性顺序是 WiX MSI -> 仅在必须链式部署 EXE prerequisite 时加 Burn -> Inno -> 只有前者仍有明确体积或特殊流程缺口才继续 NSIS。候选先按架构、无 runtime 离线启动、状态保留、许可、未签名真实下载和近最终体积淘汰，再比较自写生命周期代码量；不能先按安装器界面或空壳体积拍板。WiX 7 的 OSMF、`.NET SDK 6+` 文档与 `net8.0` 包实物差异、MSI major-upgrade 调度、Burn 非原子 EXE prerequisite、离线 Repair source/cache、跨架构迁移和事务提交后的新版健康确认边界都已进入证据登记册。
