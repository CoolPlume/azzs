## 当前已确认决定

以下决定已经确认，并覆盖本文后续第一轮建议、前置依赖与发布门槛的旧表述：

- Q4：不以信任、真实性、签名、摘要、发布者、许可、再分发或 provenance 作为用户主动更新、受控第三方安装器取得或执行的项目级阻断门槛；见 ADR-0035。
- Q5：状态主体、设备级状态、权威提交、恢复检查点、日志退化和清理边界以 ADR-0029 为准。
- Q8：未实机验证必须记录，但不阻断公开发行；见 ADR-0034。
- Q9：当前及以后候选资源都可随包和公开发布；`SEC-08` 禁止内容不属于候选资源；见 ADR-0036。
- Q10：不提供摘要、源码关联或 provenance；见 ADR-0005。
- Q7：采用八制品矩阵。标准版提供两种架构的便携版和安装版，断网救援版与超大离线版各只提供两种架构的便携版；见 ADR-0037。
- Q16：三类目录包的手动导入只在调试模式提供，普通和高级视图没有导入入口；见 ADR-0028。
- Q17：安装器结果或后置行为未知时暂停批次，不能仅凭首进程退出继续；见 ADR-0039。
- Q18：未知展示或说明内容可忽略，未知执行语义拒绝整包并保留当前有效目录；见 ADR-0038。
- Q19：活动或待恢复初始化操作优先于一键更新，更新必须延后；见 ADR-0006。
- Q20：一键更新只显示正式稳定发行，不展示 draft、预发布或其他测试发行；见 ADR-0006。
- Q21：正式产品名称为“Windows 初装工作台”，图标方向为简洁设备准备图形；`azzs` 只是仓库标识。
- Q22：第三方安装器交互按“受控自动处置 -> 工作台交互确认 -> 官方安装界面”逐级回退；见 ADR-0040。
- Q23：登录、注册、验证码、付款和个人资料步骤一律由用户在官方安装界面完成，工作台不代填、读取或保存内容；见 ADR-0040。
- Q24：已识别且可可靠处置的附加推广默认拒绝，无法可靠处置时沿 Q22 回退；见 ADR-0040。
- Q25：当前运行测试发行时，只提供用户主动的“切换到最新稳定版”，不自动降级或替换；见 ADR-0006。
- Q26：缺少同发行架构、内容版和便携版或安装版形态的正式稳定制品时，明确不能自动更新并给出手动下载入口，不自动换制品；见 ADR-0006。
- Q27：GitHub 仓库与 Release 采用“Windows 初装工作台：帮助新装 Windows 完成驱动准备、系统优化、常用软件安装和软件优化。”作为产品简介。

本文件其余部分保留为 2026-08-10 的问题树和审计依据。除本节随后明确列出的当前前沿外，其中将 Q4、Q5、Q8、Q9 或 Q10 视为未决、发布阻断或进一步提问前置的文字均已被上述决定覆盖，不再作为当前规则使用。

## 3. 每题的文档影响

### Q4：提权下载、执行与更新安全合同

- 直接冲突/需复核：ADR-0001、0005、0006、0010、0013、0027。
- 规格族：`SEC`、`SRC`、`CACHE`、`RUN`、`UPD`、`REL`。
- 主要事项：07、08、17、21、22、31；目录来源与发布事项也会受影响。
- **Q4a 自更新信任根**：推荐在没有代码签名、受信平台或独立带外首次信任根时取消一键替换，只保留浏览器手动下载；签名更新清单只能在首次 root 已可信取得后证明连续性，把公钥嵌入未签名应用本身不够。
- **Q4b 第三方安装器真实性**：推荐自动管理员执行默认要求受信签名且发布者符合该软件预期；无签名仅在有独立认证的固定摘要和逐软件批准时例外，否则外部交接。签名无效、吊销、摘要不符或验证后变化一律阻止且无绕过。
- Q4a-b 是当前前沿。Q4c-h 的建议分别是 HTTPS-only、只允许精确审核的离线快照、外置缓存仅作容量层、公开版采用窄特权代理、统一认证控制元数据、跨类别紧急安全阻止；它们按第 2 节依赖顺序在后续轮次提问。
- Q4a-h 全部回答后才冻结威胁模型、控制元数据、紧急阻止、来源/逐跳重定向、私网目标、缓存 ACL/重解析点/TOCTOU、发布者/摘要、MOTW、子进程令牌和自更新失败关闭合同。
- 不应混答：HTTPS、文件摘要、Authenticode、MOTW/SmartScreen，以及应用发布、应用自更新、第三方安装器真实性分别是不同保证。
- 一手依据与完整验证矩阵：[常驻管理员工作台的下载、缓存、执行与自更新安全研究](../../docs/research/elevated-download-execution-security.md)。

### Q8：无真实 Windows 证据能否公开发布

- 直接冲突/需复核：`未实机验证` 的领域定义、发行验收政策和事项 22 状态。
- 规格族：`REL`、`TECH`、`UI`、`SEC` 及首版必达项对应需求。
- 主要事项：21、22、24、31，以及实际制品覆盖的功能事项。
- 回答后立即动作：把开发构建与公开 Release 分开，固定 Win11 x64、Win10 22H2、ARM64、搜狗和无障碍最小矩阵及允许缺口。
- 不应混答：cross-build、静态分析和模拟器证据不能算真实 ARM64/Windows 通过。

### Q9：超大离线版是否服从权利与身份门禁

- 直接冲突/需复核：候选审核稿中的“超大离线版携带”、三档内容版承诺和证据登记册只有 `accepted` 才可发布的规则。
- 规格族：`OFF`、`REL`、`SRC`、`TECH`；主要事项：19、21、22、30、31。
- 研究已覆盖 32 个对象：4 项明确允许、5 项带条件允许、18 项当前公开镜像用途不受证据支持、3 项身份未闭合、2 个自研工具待制品化；这仍不构成任何 `accepted`。
- 推荐同时确认：超大离线版可以少带未获权利的候选；身份未闭合或许可 `NOASSERTION` 默认排除；工作台实际构建 BOM 中未知组件也阻断公开制品。
- 回答后先关闭 `REDIST-D1`、`REDIST-D7`、`REDIST-D11`，再按优先级展开 `REDIST-D2..D6`、`REDIST-D8..D10`；不要求一次决定每个软件。
- 不应混答：免费、可下载、开源仓库、安装成功和维护者本地已有，都不等于项目有权公开镜像二进制。
- 一手依据与逐项回退：[第三方二进制公开再分发基线](../../docs/research/third-party-binary-redistribution-baseline.md)。

### Q10：不签名是否仍允许完整性与来源证明

- 直接冲突/需复核：ADR-0005、`SEC-05`、`UPD-03`；GitHub Release API 当前已经提供 asset SHA-256，immutable release 与 attestation 还会关联 tag、commit 和 workflow。
- 规格族：`SEC`、`UPD`、`REL`、`TECH`；主要事项：17、21、22、30、31。
- 推荐把 Windows Authenticode 代码签名与外部 SHA-256／build provenance 分开：可以继续不签 PE，但提供最终资产 manifest、source commit、build/SBOM attestation 和长期验证材料。
- 若继续全面禁止摘要和源码关联，就必须放弃独立 checksum、build provenance 和 immutable release 的 commit 证明，且不能在发行验收中暗用这些能力。
- 回答后才展开 `RELEASE-D2..D7`：正式 builder、ARM64 路径、Win10 隔离、未签名资产信任根、canonical SBOM 与超过 Actions 90 天保留期后的证据保存。
- 不应混答：有 hash 不等于有认证发布者；attestation 不等于软件安全、可重现构建、真实 Windows 通过或许可闭合。
- 一手依据与完整证据字段：[公开构建来源、CI 与发行证据研究](../../docs/research/release-provenance-and-ci-evidence.md)。

### Q11：安装器进程架构与标准 Repair

- 直接缺口：规格要求 x64/ARM64 安装版，却没说明安装器进程能否依赖模拟；事项 21 要求安装版，但没有定义 Repair 语义。
- 规格族：`REL`、`TECH`、`SEC`、`RST`；主要事项：01、02、12、17、21、22、31。
- **Q11a 安装器进程架构**：推荐 ARM64 命名资产的 installer/bootstrapper、uninstaller、必要插件和自定义动作也原生 ARM64；否则准确披露为“模拟安装器 + 原生 ARM64 工作台”，并分别测试 Win10/Win11 on Arm。
- **Q11b 标准 Repair**：推荐安装版提供 Windows 标准 Repair，但只恢复当前版本安装器拥有的程序文件和声明资源；不得覆盖、重置或删除 ProgramData 中的状态、缓存、日志、草稿和恢复记录。
- Q11a-b 分别映射安装器研究的 `INSTALLER-D1/D2`。WiX 条款、普通卸载、可重复构建级别与跨架构迁移是同轮独立问题 Q12-Q15；其余 VC Runtime、显式删除/降级、未签名支持边界、体积、事务后健康确认和最终候选按第 2 节依赖展开。
- 不应混答：MSI/Burn 的 rollback 或 Repair 不等于应用 N/N-1 回退，也不自动保护运行时生成的数据；Burn 的 EXE prerequisite 不属于跨包 MSI 原子事务。
- 一手依据、候选顺序和故障矩阵：[传统 Windows 安装器候选研究](../../docs/research/traditional-installer-options.md)。

### Q12：WiX 7 官方二进制工具条款

- 直接缺口：WiX 7 源码使用 MS-RL，但官方 Binary Release 另受 OSMF EULA；另付支持费只豁免 Fee，不豁免 EULA。
- 主要影响：构建工具取得路径、CI 的显式 EULA 接受、工具链版本锁与 WiX 是否继续进入样机。
- 推荐按项目实际用途书面记录适用性，不默认豁免；若既不接受官方条款也不愿长期维护源码自编，立即淘汰 WiX，直接从 Inno 基线继续。
- 不应混答：源码许可不自动覆盖官方预编译工具；网页收入阈值摘要也不能替代随包 EULA 文本。

### Q13：普通卸载与 ProgramData 保留

- 直接缺口：现有正式决定只明确保留已生效设置与恢复记录，尚未逐类覆盖历史、目录、草稿、检查点、偏好、缓存和日志。
- 主要影响：Q5 后续卸载矩阵、`INSTALLER-D5/D6`，以及 MSI `RemoveFile`、Inno `[UninstallDelete]`、NSIS 删除脚本的允许范围。
- 推荐普通卸载只删除可重建程序文件和登记，完整 ProgramData 默认保留；显式“删除本机数据”另作受保护核心用例，并等待 Q5f-k 的主体/分类答案。
- 不应混答：保守保留策略不是永久承诺所有缓存永不清理，也不授权安装器递归猜删稳定设备根。

### Q14：安装器可重复构建级别

- 直接缺口：固定输入能稳定构建成功与跨干净 builder 的 bit-for-bit 相同是两级不同承诺。
- 主要影响：`INSTALLER-D9`、正式 builder、版本锁、时间戳/压缩/GUID/绝对路径归一化和两次构建对账。
- 推荐首版先要求精确版本、锁定输入、两次构建差异可解释并保留最终摘要；只有明确需要时才把 bit-for-bit 设为发布阻断。
- 不应混答：`notimestamp`、`SOURCE_DATE_EPOCH` 或单次摘要一致都不能单独证明跨 builder 可重现。

### Q15：ARM64 上既有 x64 安装版迁移

- 直接缺口：规格要求 ARM64 Windows 使用 ARM64 包，但没有定义设备已经安装 x64 版本时的产品身份、ARP 登记、卸载顺序和共享状态结果。
- 主要影响：`INSTALLER-D13`、安装/升级矩阵、便携/安装切换、ProgramData 并发和用户可见迁移文案。
- 推荐 ARM64 首次安装只使用原生 ARM64 资产；既有 x64 安装版采用互斥的受控替换，保留共享设备状态并清理旧程序登记。
- 不应混答：Windows 可以模拟运行 x64 程序，不代表两种架构的安装版可以静默并存并共同写同一状态根。

### Q2：救援伴随工具质量责任

- 直接冲突/需复核：ADR-0001、0003、0027，架构规范和候选审核稿。
- 规格族：`DRV`、`OFF`、`SEC`、`REL`、`RUN`。
- 主要事项：14、19、21、22、31；可能需要独立制品接入事项。
- 回答后立即动作：决定是否需要源码/可复现构建/许可/摘要/令牌合同/冒烟测试，或把入口降为外部交接。
- 不应混答：维护者拥有工具不自动等于工作台项目可以不测试却以管理员令牌启动。

### Q3：U 盘厂商网卡驱动边界

- 直接冲突/需复核：ADR-0009；如果工作台安装，必须由新 ADR 明确 supersede。
- 规格族：`DRV`、`SEC`、`LOG`、`REL`。
- 主要事项：02、08、14、16、19、21、22、31。
- 回答后立即动作：若外部交接，只定义说明、位置选择、记录和返回检测；若受控安装，新增 INF/EXE 身份、适用性、签名、介质换包和恢复安全模型。
- 不应混答：打开 U 盘位置与把文件交给管理员工作台执行是不同能力。

### Q7：三档内容版与制品矩阵

- 当前状态：第二轮前沿；Q2、Q3、Q4、Q8、Q9、Q10 已确认。
- 直接冲突/需复核：ADR-0012；需要新 ADR 显式 supersede，而不是原文静默改成三档。
- 规格族：`OFF`、`REL`、`TECH`、`DRV`、`CACHE`。

- 不应混答：内容版不改变核心、安全边界或默认勾选；安装版/便携版也不是内容版。
- 可比较选项：[方案 1（12 个成品）、方案 2（8 个成品）与方案 3（应用/资源分离）](release-artifact-matrix-options.md)。当前推荐方案 2。

### Q5：持久化与 Windows 用户合同包

- 直接冲突/需复核：ADR-0004、0007、0013、0014；`CAT-51`、`DBG-10`；当前“设备级”不能代表所有记录都无主体，“保存成功”也不能无条件承诺任意硬件断电后绝对恢复。
- 规格族：`LOG`、`RST`、`CACHE`、`HIST`、`DBG`、`SET`、`OPT`。
- 主要事项：02、03、07、10、11、12、15、18、25、31、32。
- **Q5a 身份模型**：推荐首版只支持登录用户用自己的拆分管理员令牌提权；替代管理员凭据场景准确阻止，不在单进程里猜状态主体。
- **Q5b 介质与耐久边界**：推荐权威状态只放本机 `ProgramData`；网络/移动位置只承载缓存。成功需刷新、替换和重读校验，但物理断电承诺受文件系统、驱动和硬件兑现刷新请求的边界约束。
- **Q5c 版本窗口**：推荐首版保证 N 与 N-1；旧版遇到未知新模式保留字节并拒绝写入，不能初始化或降级。
- **Q5d 共享缓存并发**：推荐只保证同机多实例；网络共享可以作为位置，但不保证多台电脑同时写，跨主机并发另立 SMB 合同。
- **Q5e 未保存检查点**：推荐最多丢失 10 秒；语义编辑后防抖，并在达到上限、应用失活和高风险操作前检查点。WER 回调只作补充。
- Q5a-e 是当前前沿；回答后只会解锁 Q5f-i，不能立即宣称完整持久化合同已经冻结。Q5j-l 还依赖第二轮答案。
- Q5a-l 全部回答后才写最终 scope/subject、SID/ACL、每类状态模式、迁移与 N/N-1 回退、权威提交、损坏回退、锁、检查点墓碑、日志退化、卸载保留和真实故障注入合同。
- 不应混答：存储目录可以设备共享，记录的业务作用域仍可以是用户级。
- 一手依据与完整后续分支：[Windows 状态持久化与恢复合同研究](../../docs/research/windows-state-persistence-and-recovery.md)。

### Q6：软件当前状态与操作结果

- 规格族：`SW`、`RUN`、`FLOW`、`LOG`、`HIST`、`UI`。

- 不应混答：检测到软件存在不能证明本次由工作台安装成功，也不能证明是最新版或来源正确。

### Q1：恢复的未保存修改如何呈现

- 已确认前提：异常退出/断电后尽量找回；内容仍未保存，不自动保存、应用或覆盖；找回失败不伪报成功。

- 不应混答：呈现方式不决定自动保存频率、磁盘格式或崩溃一致性实现。

## 4. 工程团队可自行用样机解决的事项

以下问题不要求维护者凭偏好提前拍板；先做最小工具链或安全样机，再按证据选择：

- MSBuild/WinUI 宿主与 CMake/CTest 可移植核心的具体装配方式。
- `/MT`、app-local VC Runtime 或安装器捆绑 Redistributable 的可行性。
- 传统未签名安装器的具体技术选型：同一近真实负载先测 WiX MSI；只有确需 EXE prerequisite 才加 Burn；再用 Inno 对照；NSIS 只有明确收益才继续。
- 原子文件替换、flush、锁和损坏回退的 Windows API 组合。
- Graphify/GitNexus、目录模式校验和文档检查在 CI 中的具体命令。

唯一例外是这些工程选型若要推翻既有 ADR、增加第三方可执行插件、改变公开承诺或扩大数据收集范围，必须回到维护者确认。
