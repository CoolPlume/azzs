## 1. 判定类别

| 类别 | 含义 |
| --- | --- |
| A | 决定与当前正式规格一致，继续保留 |
| B | 后续确认已经改变方向，但正式 ADR/规格尚未同步 |
| C | 存在真实产品或风险取舍，必须由维护者选择 |
| D | 决定仍成立，只需术语、链接或元数据同步 |

## 2. P0 冲突

### 三档内容版与 ADR-0012

标准版、断网救援版、超大离线版已经有确认记录；ADR-0012 和正式规格仍是在线版/离线资源版两档，属于 B。实际制品矩阵和救援内容责任仍未决，因此应等 Q2/Q3/Q7 后新建 ADR，显式标记 ADR-0012 被替代，不直接改写旧决定。

### 救援伴随工具与 ADR-0027

候选稿称两个独立 EXE 随包、由工作台启动，但不由本项目实现或测试；ADR-0027、架构规范和 `SEC-07` 要求提权能力经过同一项目检查，属于 C。

- 若工具成为有源码、可复现构建、稳定版本、许可、完整性、进程令牌合同和最小测试的受控制品，ADR-0027 可保留。
- 若只做外部交接且不从提权工作台启动，ADR-0027 也可保留。
- 若坚持捆绑并启动不受控 EXE，必须用明确安全例外 ADR 取代现有边界，不能只改措辞。

### U 盘厂商网卡驱动与 ADR-0009

“导入”可能是外部交接，也可能是选择、验证或安装 INF/EXE，属于 C。若只是说明、打开位置和记录，保留 ADR-0009，并统一为“本地驱动交接”；若由工作台安装，则先定义信任、签名、适用性、回滚和日志合同，再用新 ADR supersede ADR-0009。

### 常驻管理员、不签名、自更新与第三方安装器

ADR-0001、0005、0006、0010 的文本并非互相矛盾，但组合后存在真实性缺口，属于 C。风险披露、确认和失败回滚不能阻止被替换的二进制取得管理员权限。Q4 后应保留或重新审议各自决定，并用独立安全 ADR 分别处理应用更新、第三方包、目录包和紧急通知的真实性；不要把来源优先级与“拒绝验证”写成同一决定。

### 不签名发行与 GitHub 来源证明

ADR-0005 把“不做 Windows 代码签名”“不提供 SHA-256”“不关联源码提交”绑定为一个决定；GitHub 当前 Release asset API 已显示 `sha256:` digest，immutable release 和 build attestation 还会关联 tag、commit 与 workflow，属于 C。Q10 必须明确平台已有 digest 是否也被禁止。建议保留“不做 Authenticode”这一取舍，但用新的发行来源 ADR supersede 无摘要／无源码关联部分，并分别定义 checksum manifest、build/SBOM attestation、首信任和长期证据保留；否则必须放弃相关验证能力，不能在发行验收中暗用。事实依据见[公开构建来源、CI 与发行证据研究](../../docs/research/release-provenance-and-ci-evidence.md)。

### 设备级状态与用户级事实

ADR-0004 把设置原值概括成设备事实，规格又统一放公共应用数据；HKCU 和用户配置不能跨 Windows 用户共用无主体记录，属于 C。Q5 后建议用“状态作用域与主体隔离”ADR supersede ADR-0004：存储位置可以设备共享，记录显式区分 `machine/user`，用户级事实按 SID 与 ACL 隔离。ADR-0026 的用户界面分类决定不回答存储主体问题。

### C++26 与 ADR-0022

MSVC 没有 `/std:c++26`，而 `/std:c++latest` 会开放进行中或实验能力；ADR-0022 与技术基线同时要求 C++26 编译模式和不依赖实验能力，属于 C。先做零产品功能样机；若 C++26 是目标口径，可补充固定编译器加特性允许清单，若要求正式标准开关，则需调整语言基线并 supersede ADR-0022。

## 4. 不需要 ADR 的同步

- 基础软件“缺少则安装、旧版更新、最新版不重装”已有确认记录，但正式 `SW-12/SW-13` 仍是检测到已安装就跳过；这是规格落后，不需要新 ADR。
- 候选审核稿 1-11 项的过期 `proposal/pending` 表头已在本轮修正为 `reviewed-candidate`，同时明确许可、安全责任与制品矩阵仍开放。
- 崩溃后找回的内容仍是未保存修改、不自动保存或应用，这一语义已在 ADR-0028、`DBG-10` 和交接记录中一致；启动呈现仍待另一任务确认，`CAT-51`/`DBG-10` 的绝对断电耐久措辞及完整持久化合同仍受 Q5 树阻塞。是否需要新的持久化 ADR 应在这些决定后判断。
- 若 Q8 改变“无真实 Windows 证据也可公开发布”的政策，建议用单独 ADR 记录发布证据门槛；如果只补测试计划而不改变门槛，则更新规格和事项即可。

## 5. 推荐执行顺序

1. 先完成当前前沿 Q4a-b/Q10/Q8/Q9/Q2/Q3/Q11a-b/Q12-Q15/Q5a-e/Q6，再按依赖展开 Q4c-h、Q5f-l、`REDIST-D2..D10`、`RELEASE-D2..D7`、其余 `INSTALLER-D*` 与 Q7；Q1 由另一任务单独收口。
2. 决定哪些旧 ADR 被保留、补充或 supersede；先写决定和理由，再同步规格。
3. 把三档、基础软件更新语义和安全/持久化合同转成新的原子需求。
4. 重跑需求覆盖、事项依赖、术语和文档链接检查。
5. 在样机证据出现前，不把精确工具链、CRT 或安装器候选写成已接受 ADR。
