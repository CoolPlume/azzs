### 1.1 领域状态词补充（06:32）

领域词汇复核未产生新的独立票据，但把以下四个交叉风险加入现有工作包的完成定义：

- 事项 14/16 与 Q3/Q17：驱动或外部安装交接必须区分“用户/厂商尚未交接”“工作台已观察”“需要重启”“重启后待验证”和流程聚合结果；不能用一个“已完成”覆盖这些阶段。
- 事项 08/12/16 与 Q6/Q17：流程完成只允许在步骤结果、暂时跳过、外部已识别和待确认状态按正式聚合规则收敛后成立；存在未决步骤时应保留可恢复/待确认结果。
- 事项 19/21/22/32 与 Q6/Q16/Q18：目录导入或应用结果必须与本机试用身份、目录校验结果和公开发布证据分层；未知执行语义拒绝整包，未知展示内容不得伪报为执行语义。
- 文档权威审计与事项 30/31：`Status: confirmed` 等文档标签要明确作用域，不能被当成全部产品决策、实现或发布证据已经确认。

上述条目仍是 `needs-info` 的负向验收补充；没有替维护者回答 Q，也没有提升事项状态。

## 4. 建议拆票顺序

1. 不改现有 01-32 编号前，先确认事项 31/32 和 30 的拆分方案，避免新票编号冲突。
2. 第一批新票只承载工具链样机、安全威胁模型、持久化合同、许可台账和文档/追踪整理，不开始产品功能。
3. 决策回答后，再建立三档发行、受控救援/外部交接、目录模式和发布证据票。
4. 每张票只指定一个合同所有者；其他事项以消费者身份引用，不复制完整验收。
5. 任何需要真实 Windows 的票明确区分“可由 agent 完成的文档/构建准备”和“需人在机器上执行的证据”，使用 `ready-for-agent` 与 `ready-for-human` 分开。

## 5. 开始产品实现的退出条件

- Q2/Q3/Q11a-b/Q12-Q15/Q7/Q16-Q27 及适用的 `INSTALLER-D3/D6-D8/D10-D12/D14` 已按依赖树形成明确答案；Q1 只要不阻塞核心恢复接口即可稍后完成。Q4、Q5、Q8、Q9、Q10 与 Q6 已确认，不再列为退出条件。
- 新旧 ADR 的保留/supersede 关系清楚，正式规格已吸收三档和基础软件更新语义。
- 事项图无形式环、无语义闭环，所有原子需求有明确 owner。
- 工具链样机证明 x64/ARM64 构建、自包含、CRT 和干净机启动的可行路径。
- 安装器同负载样机证明所选生命周期不会删除或覆盖应保留状态，且 x64/ARM64、跨架构迁移、升级/降级、失败、离线 repair/重装、卸载、未签名和体积边界有明确证据；安装事务后的新版健康确认与 N-1 恢复另由应用更新合同闭合。
- 威胁模型与持久化合同形成可测试边界。
- 软件目录模式能表达首版规则，目录内容和再分发证据仍可分批补齐。
- CI/发布记录能在没有 UI 的情况下验证核心，并如实标记真实 Windows 是否未实机验证。
- 公开源码与公开 Release 仍分别授权；候选资源的来源、许可、身份和再分发事实不构成项目级发行门槛。
