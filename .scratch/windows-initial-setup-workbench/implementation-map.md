- 以下八个实施部分已经冻结；五条实现线是部分内部的并行容量，不是另外五个交付阶段。
- 每个活动事项使用独立 worktree 和短期 `codex/*` 分支，共同基于 `codex/v1-integration`；核心接口、目录模式和持久化合同分别由单一集成负责人修改，不建立五条长期分叉。
- `Status:` 继续记录五个 canonical triage 角色，`Resolution:` 独立记录 `open`、`completed` 或 `wontfix`；只有 `completed` 自动解除 `Blocked by`。

## Codex 会话编排合同

- 当前会话是常驻协调与集成负责人；一张 `ready-for-agent` 原子事项对应一个短期 Codex 任务，八个实施部分不建立长期开发会话。
- 每个任务从最新 `codex/v1-integration` 提交建立独立 worktree，使用 `codex/issue-NN-*` 分支并继承 Codex 默认模型与推理强度。任务可以认领事项、修改文件、运行验证和本地提交，但不得自行合并、推送、修改 GitHub 设置、创建 tag/Release 或发布制品。
- 任务结束必须报告事项号、任务 ID、分支、提交、修改范围、执行命令、通过与失败证据、未验证项、风险和建议结论；任务不得自行宣布结票。协调会话独立复验后，以每事项一个 squash 提交合入集成分支，在事项 `## Answer` 保留任务、PR、原始提交和验证入口，再设置 `Resolution: completed`。
- `codex/v1-integration` 和进入 CI 的候选分支公开可见。早期 CI 只在同仓库拉取请求指向集成分支、集成分支或 `main` 更新及人工触发时运行；不使用 `pull_request_target`、secrets、写权限或 self-hosted runner，事项 21 前不上传可下载应用二进制。
- 每次事项完成后按 `Blocked by` 机械重算完整前沿，在五线容量内自动创建下一批任务，不逐波等待确认。规格或 ADR 变化、GitNexus 高风险或严重影响、CI 失败、所有权冲突、`ready-for-human`、`needs-info` 或未授权外部动作会暂停自动推进并交由维护者决定。
- `main` 不接收逐事项开发提交。G1、ADR-0045 和早期 CI 基线由协调会话准备 PR 后等待维护者明确允许合并；功能完整 beta 按事项 34 的自动发布合同晋级；`v1.0.0` 始终等待事项 35 的独立人工授权。
