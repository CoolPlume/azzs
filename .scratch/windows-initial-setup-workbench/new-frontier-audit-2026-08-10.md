## 1. Q16：手动导入目录的支持边界与信任模型

### 证据

- 规格称普通使用模式不正式支持普通用户自制目录，但仍允许高级设置页的手动导入入口（[spec.md:48](spec.md:48)、[spec.md:538-539](spec.md:538)）。
- 导入文件的来源无法验证，确认后可以成为当前有效目录，并决定后续管理员操作；运行时通过但未通过正式发布门禁时标为本机试用目录。
- 调试模式编辑器与设置页导入共用本机试用目录身份，但两者的操作者、支持责任、回退入口和故障归因没有分开定义。

### 未闭合的决策

1. 普通用户是否可以在高级视图中导入任意未签名软件目录，还是只有显式调试模式/维护者工作流可以导入？
2. 若允许，工作台是否承诺支持该目录驱动的行为，还是只承诺“结构可加载的本机试用”？导入来源、原始字节、修订、应用关联标识、操作者和回退点保留多久？
3. 导入目录如何回到内置或上一份可信目录？回退是否阻止当前有效目录已有的进行中批次、待重启状态和历史继续执行？
4. 导入动作是否需要再次确认“常驻管理员会话将按未验证目录执行”，以及是否在缺少项目身份、模式最低版本或安全能力声明时直接失败？

### 推荐默认值（待维护者确认）

首版不在普通用户流程承诺任意未验证目录；只在显式调试模式中允许导入，并持续标注“本机试用目录”。导入仍只能表达已建模目录数据，不能携带脚本、解析代码、安装参数或插件；应保存来源与应用关联记录，提供恢复内置/上一份可用目录的明确入口，并在导入前后重复显示管理员执行风险。若产品坚持在普通高级视图开放该能力，应另立安全/产品 ADR，明确支持责任、权限边界、回退和数据保留，不能继续借“用户确认”四字代替信任模型。

**优先级：P0/P1。** 这是目录能力范围与高完整性执行边界的冲突，至少阻塞目录生命周期和发布安全验收。

## 2. Q17：第三方安装器的重启及后置副作用合同

### 证据

- 批次执行器目前只规定安装器退出后按目录规则检测结果；`install_profile` 只被引用，没有统一声明重启、子进程、服务或完成信号的字段（[issue 08:20-25](issues/08-installation-batch-runner.md:20)）。
- 工作台不自动重启 Windows，但官方安装器可能继续运行、要求重启或留下服务/驱动/登录后动作；普通重启屏障只描述初始化操作的泛化恢复（[spec.md:90-96](spec.md:90)）。
- 安装器研究已经区分“安装器事务成功”和“应用新版健康确认”，但尚未把第三方软件安装批次的后置进程合同写入安装档案（[traditional-installer-options.md:395-396](../../docs/research/traditional-installer-options.md:395)）。

### 未闭合的决策

1. `install_profile` 是否必须声明重启行为（不需要、要求用户重启、安装器主动重启、异常重启）及其对后续项目的阻止规则？
2. 如何界定安装器的完整进程树：首进程退出但子进程仍在、服务已注册但安装器返回成功、安装器启动后再下载载荷时，何时算“安装器结束”？
3. 返回码、文件/注册表检测、服务状态和目标软件启动检测之间的优先级是什么？无法确认时是否统一进入“安装结果待确认”并暂停批次？
4. Windows 重启后由谁验证后置安装步骤、服务/驱动状态和目标软件版本？异常重启是否阻止下一项，还是可在只读验证后继续？
5. 关闭工作台时，用户已启动的安装器/子进程/服务是否允许继续；下次启动怎样绑定到原批次项目而不是仅凭显示名或陈旧 PID 猜测？

### 推荐默认值（待维护者确认）

把重启策略、后置进程边界、服务/驱动副作用、完成信号、结果检测器、重启后验证和失败关闭规则纳入每个受控安装档案。任何未声明或无法确认的后置行为默认暂停当前批次并显示“安装结果待确认”，不得启动下一项；恢复时只读验证捕获的安装身份和结果，再由用户明确继续。安装器退出码不能单独代表整棵安装流程完成。

**优先级：P1，涉及首版必达软件时升为 P0。** 它直接影响串行批次、重启恢复、安装结果和管理员令牌的责任边界。

## 3. Q18：目录模式安全字段的向前兼容规则

### 证据

- 目录加载允许忽略未知字段，但未知 `schema_version` 必须拒绝整包（[spec.md:519](spec.md:519)、[spec.md:579](spec.md:579)）。
- 当前规则没有区分展示/本地化字段与会改变来源真实性、用户同意、执行能力、风险确认、紧急阻止或撤回语义的安全字段。
- 三类目录、应用更新和紧急控制元数据都可能在常驻管理员会话中改变后续操作；旧工作台若静默忽略新增安全字段，可能继续执行缺少新门禁的目录。

### 未闭合的决策

1. 哪些字段被归类为安全关键能力；新增此类字段时是否强制递增模式版本并声明最低工作台版本？
2. 是否增加 `min_workbench_version`/能力集合/安全策略代次等显式字段，旧工作台遇到未知安全能力时一律拒绝加载而不是忽略？
3. “未知字段可忽略”是否只适用于不影响执行的显示、教育和本地化扩展？未知字段被忽略时是否记录诊断事件并在本机试用身份中可见？
4. 三类目录的模式版本、应用更新清单和紧急阻止元数据是否采用同一兼容窗口；模式降级、回退和跨发行架构如何配对？

### 推荐默认值（待维护者确认）

把字段分为非安全扩展和安全能力扩展：前者可按现有规则忽略并记录；后者必须通过递增 `schema_version` 或能力代次、声明最低工作台版本并在旧工作台上失败关闭。未知安全能力、用户同意要求、来源真实性、执行器/结果检测器、紧急阻止和撤回字段默认拒绝，不能因 `release_state = "draft"` 或用户确认导入而绕过。为每类目录提供“旧工作台读取新目录”的负向测试和迁移/回退规则。

**优先级：P1。** 这是目录/更新向前兼容与安全默认值的供应链门禁。

## 4. Q19：应用更新健康检查与回退触发条件

### 证据

- 规格仅要求下载、替换或新版启动失败时恢复上一版本（[spec.md:675-680](spec.md:675)）；事项 17 也只写“新版启动失败”这一粗粒度条件（[issue 17:13-18](issues/17-application-update.md:13)）。
- 安装器研究明确要求区分“安装事务完成”和“应用更新成功”，并记录启动健康确认及 N-1 资产责任（[traditional-installer-options.md:395-396](../../docs/research/traditional-installer-options.md:395)、[traditional-installer-options.md:478-480](../../docs/research/traditional-installer-options.md:478)）。
- 现有合同没有定义启动成功、状态迁移失败、启动后崩溃、健康检查超时、管理员批次占用、回退失败或回退后状态代次不兼容的判定。

### 未闭合的决策

1. “新版启动成功”是否至少包括进程达到可交互就绪、核心状态迁移与读取校验成功、目录可加载、关键依赖装配成功，并在宽限期内未崩溃？各超时是多少？
2. 更新开始时若有安装批次、优化批次、重启屏障、目录应用或恢复写入，是否阻止/延迟更新；如何告知用户不会丢失当前任务？
3. 新版启动后崩溃、状态迁移失败或健康超时是否一律回到 N-1；回退也失败时如何保留 N、N-1、诊断证据和可恢复入口，避免第三次覆盖？
4. 更新通道（stable/prerelease/draft）、发行架构和便携/安装形态的候选过滤、严格版本比较及普通降级阻止是否由同一更新协调者拥有？
5. 安装器返回成功但应用健康失败时，最终用户结果显示“安装成功”还是“更新失败/结果待确认”？历史和发布证据如何分别记录两个结果？

### 推荐默认值（待维护者确认）

把“安装器包事务成功”和“应用更新成功”建模为两个结果。应用更新协调者负责停止运行实例、保留 N-1、启动新版并在固定超时内完成核心状态读取/迁移、目录加载和无崩溃健康检查；任何阶段失败都回退到 N-1。更新期间存在活动批次、重启屏障或高风险持久化提交时默认拒绝或延迟。N 与 N-1 均无法恢复时保留两套字节和诊断证据，进入显式不可修改/恢复流程，不以空状态或第三次安装覆盖。

**优先级：P0。** 该合同决定自更新是否会把管理员工作台和设备状态同时置于不可恢复状态。

## 5. 敌对复核细分：作为 Q17/Q19 的子合同

这些不是新的根问题，避免把决策树拆得过细；但它们必须在相应合同关闭前进入验收和状态模型：

1. **批次占用释放点（P1）**：锁释放不等于批次占用释放。安装器根进程返回、允许的后代进程/服务收敛、结果检测完成或“结果待确认”已落盘、待重启屏障建立，哪个事件才释放设备占用？强制终止或后代仍存活时，第二实例是否只能只读。依据：[状态研究](../../docs/research/windows-state-persistence-and-recovery.md:221)与[安全研究](../../docs/research/elevated-download-execution-security.md:168)。
2. **结果检测器无副作用（P1）**：`install_profile` 的结果检测器必须声明只读目标、固定身份、超时和未知结果；不得因检测而启动目标软件、联网、改注册表/服务或重跑安装。异常统一进入“安装结果待确认”，并保留“意图已持久化 -> 外部效果可能发生 -> 效果已观察 -> 结果已确认”的阶段记录。
3. **一键更新与活动批次互斥（P1）**：存在活动安装/优化、待确认、待重启、待恢复批次或外部安装器时，一键更新是阻止、排队，还是要求先停止并保存；更新助手怎样取得设备锁，避免替换仍被批次占用的文件。它属于 Q19 的并发前置，不由健康检查单独解决。
4. **重启屏障的一次性启动注册清理（P1）**：`RST-03` 要求登录后一次性打开，但还没有定义启动注册的用户/SID、创建与清理时机、第二用户、取消、卸载、更新失败和崩溃循环。若保留，应只打开恢复入口而不静默继续管理员动作，并在完成/取消/失效时清理；否则需删除该自动打开承诺。它与 Q1 的“如何呈现恢复内容”不同，前者是启动副作用和生命周期。
5. **来源手动交接的并发边界（P1）**：外部浏览器安装不属于工作台批次，但可能在活动批次/待重启期间改变目标软件和依赖。需选择“交接建立设备级占用”或“允许并发但任何新修改前强制重新检测”，并覆盖驱动交接。
6. **驱动助手是否接入安装器合同（P1）**：`DRV-10..15` 暗示助手未安装时可由入口安装，却没有来源、版本/架构、条款、结果检测、重启副作用、回退和互斥。应明确复用软件安装档案的完整合同，或把首版入口降为纯外部交接；不要让实现者自行猜测。

## 6. 06:40 状态词落地细化（不新增根问题）

领域词汇复核把本节四组风险进一步压成可验收字段。它们仍归 Q3/Q6/Q16/Q17/Q18/Q19 及事项 03、06、08、12、14、15、16、18、19、21、22、32；本节不替维护者确定最终枚举名称。

### 6.1 驱动和外部交接

`DRV-13/14` 中的“驱动交接中”可能覆盖打开厂商页、启动助手或助手安装；“已完成”可能是用户确认、外部结果或工作台验证；“需要重启”可能是外部声明、用户选择、已建立屏障或待验证状态。最小合同应记录 `entry_id`/目标身份、`handoff_id` 与 attempt、主体/操作者、启动时间、外部结果来源、重启要求、屏障/恢复 ID、用户选择、观察时间和证据引用。正向路径是启动前持久化交接，再在返回或重开后只读展示待确认，由用户选择；选择需要重启后才建立屏障，重启后完成只读复核再继续。无返回、陈旧 PID、外部工具仍在运行、页面关闭、用户口述或重启后未复核都不得生成自动“驱动已完成”；“暂时跳过”须保留未完成/重试入口。

### 6.2 流程总结与聚合结果

`FLOW-06/07` 应拆成流程生命周期（总结显示、暂停、关闭）和逐项/逐阶段结果聚合。聚合记录至少包含 `flow_id`、stage/item ID、聚合规则版本、item status 与 operation result、阻塞原因、resume/barrier ID、重试资格、批次/操作引用、用户确认事件、观察时间和历史/日志引用。存在结果待确认、外部交接未继续、等待重启/资源管理器重启、紧急撤回或暂时跳过时，可以显示总结，但不得无条件聚合为 `completed`；仅展示总结、全项跳过或用户确认外部动作也不能伪造成功，恢复后未点击继续不得自动推进。

### 6.3 目录保存、应用与导入

“应用/导入成功”是命令或来源动作结果，不是目录身份。候选结果矩阵至少要覆盖：取消；整包运行时错误或未知安全能力导致 `rejected/failed` 并保留旧目录；运行时通过但局部依赖错误时按规则 `applied` 并禁用受影响项；运行时通过但发布级未过时为 `applied` + `catalog_identity=local-trial`；提交结果不明时为 `unknown` 且禁止继续使用新目录。证据字段至少包括 `operation_id`/attempt、source kind、操作者/主体、候选修订和摘要、运行时校验、发布门禁、本机试用标记、提交结果、替换代次、用户同意、观察时间和证据引用。用户同意导入只证明其接受加载风险，不证明来源可信、签名/摘要存在或发布门禁通过；旧批次不得重读新目录。

### 6.4 软件来源手动交接与驱动交接的差异

软件已有“外部安装已识别”路径，但它只更新目标存在事实，不能当作安装操作结果；应统一记录 `handoff_id`/attempt、软件稳定标识、原解析失败、原始地址、交接时间、每次主动重检、版本/架构可信度、未完成列表、流程续接点和用户“继续”事件。驱动如果仍是纯外部交接，则只记录入口/目标、用户确认和硬件/网络/显示/重启观察，不复用软件的“目标存在已识别”语义。恢复时两类都不得自动打开地址、下载、检测或继续修改；并发边界仍待 Q3/Q17 冻结。

以上细化是事项和测试的输入，不是实现已通过的证据；建议每个场景同时保留正常、未返回/未知、重启恢复和重复调用四类测试样例。

## 8. 07:32 复核结论

再次对照规格、事项、ADR 和研究材料后，Q16-Q19 仍是既有决策的前沿子合同，没有产生新的独立根问题。该结论只说明审计差集稳定，不代表任何推荐值已确认；在维护者回答前，不应把对应事项提升为可实现或把本机试用、安装器返回成功、目录可加载、更新包事务成功写成公开能力。
