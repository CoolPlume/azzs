## 结论

本轮没有发现一个足以取代既有 P0/P1 根问题、或需要另立产品方向的独立根问题。已有前沿审计中的 Q2-Q19、首版软件集合权威、状态词汇分层、事项 31/32 语义闭环和所有权缺口仍然成立。

但是，当前文档把若干必须跨功能保持一致的合同分散在规格和事项正文中，尚未形成可执行的横切附录。若不先收口，多个 agent 可以各自满足局部验收，却实现出互相矛盾的重试、恢复、并发或证据结论。下列条目应在开始产品实现前补入一个由维护者批准的横切合同附录，或明确链接到已有权威章节。

## 1. Owner、consumer 与 verification 三元关系

### 观察

- 32 张事项只有 `Type`、`Status`、`Blocked by` 和 `References`，没有机器可读的 `Owner`、`Consumer`、`Verification` 或 `Evidence` 字段。见 `.scratch/windows-initial-setup-workbench/issues/01-...md` 至 `32-...md` 的文件头；`rg -n '^(Owner|Consumer|Verification|Evidence):' .scratch/windows-initial-setup-workbench/issues` 无结果。
- 501/501 需求被事项引用，只能证明覆盖，不证明谁拥有事实、谁消费合同或哪一项检查可以关闭它。既有证据见 [issue-coverage-audit-2026-08-10.md](issue-coverage-audit-2026-08-10.md) 第 1 节和 [morning-owner-evidence-matrix-2026-08-10.md](morning-owner-evidence-matrix-2026-08-10.md) 第 1 节。
- 同一关系在正文中经常同时表示前置、消费和证据协作。例如事项 01 消费事项 31 的架构合同，事项 18 消费事项 32 的编辑器能力，事项 24 消费事项 18/32 的界面状态；这些关系未必是执行阻塞，却容易被误读为 `Blocked by`。

### 横切附录应冻结

每个需求 ID 至少有以下字段：

```text
owner_issue       唯一事实/规则 owner
consumer_issues   只读消费该合同的事项
verification_kind 自动检查 / 核心测试 / 适配器合同 / UI / 实机 / 人工审查
verification_id   测试、检查或证据条目的稳定标识
evidence_location 结果文件、日志或发布记录位置
freshness_policy  证据有效期、适用构建/版本/设备矩阵
```

`Blocked by` 仅表示执行前置；consumer 和 verification 关系不得隐式升级为阻塞。一个需求只能有一个 owner；若规则由多个模块协作，owner 仍拥有最终结论，其他模块列为 consumer 或证据提供者。

## 2. 三轴状态与标签语义

### 观察

- 事项 `Status` 把“可以交给 agent 处理”和“实现/证据/发行是否通过”放在同一标签空间；[morning-owner-evidence-matrix-2026-08-10.md](morning-owner-evidence-matrix-2026-08-10.md) 已指出 `ready-for-agent` 不能等同于可开工或可发布。
- `CONTEXT.md:97-103` 将 `未实机验证` 限定在开发者发布证据，但 [spec.md:900-906](spec.md) 仍允许“未实机验证”不阻止发行；这与 Q8 的待决公开 Release 门槛并存。
- `CONTEXT.md:147-161` 已区分 `release_state`、运行时加载校验和本机试用目录，但事项和规格仍交替使用“已完成”“安装完成”“已安装”等词。Q6 要求把当前软件状态与本次操作结果分层，尚未同步到所有消费者。

### 横切附录应冻结

所有事项、证据和 UI 文案使用三轴，且禁止由一个标签推导另两轴：

1. 规格轴：`proposed`、`confirmed`、`needs-info`、`superseded`。
2. 工程轴：`not-started`、`in-progress`、`automated-pass`、`contract-pass`、`hardware-pass`、`failed`。
3. 发行轴：`draft`、`candidate`、`public`；第三方资源另有 `accepted`/`excluded`/`unknown`。

业务运行时还要分别建模当前状态、计划/批次状态、本次操作结果、恢复状态和发布身份。`已安装`只能表示检测到的当前事实；不能由它推导“本次安装成功”“来源可信”或“最新版”。

## 3. 证据时间、新鲜度和适用范围

### 观察

- 研究文件带有研究日期和来源，但证据登记中的条目尚未统一要求取得时间、目标构建、Windows 版本、架构、目录修订或通知修订。见 [preimplementation-evidence-register.md](preimplementation-evidence-register.md) 第 1-4 节。
- `OPT-45/46`（[spec.md:958-959](spec.md)）对紧急撤回通知保留“上次成功取得时间”，但普通软件来源解析、应用更新、安装器后置结果、实机发布证据没有同一个 freshness/expiry 规则。
- 事项 06 已保存来源解析时间，事项 08 冻结解析时间；但没有全局规则说明何时旧解析结果必须失效、重试能否重用旧字节、目录或安全通知更新后哪些快照仍可执行。

### 横切附录应冻结

每个外部事实和发布证据必须包含：`observed_at`、`source_revision` 或资产摘要、`target_build`、`architecture`、`catalog_revision`、`policy_revision`、`expires_at`/`freshness_class` 及失败时的“不确定”状态。执行前必须按 owner 定义的时效策略重新验证；过期或无法关联到当前快照的事实只能触发重新检测、暂停或外部交接，不得静默当成通过。

证据应区分：

- 设计/文档证据：证明合同已写明；
- 自动检查证据：绑定 source commit、工具链和测试输入；
- 平台合同证据：绑定适配器版本及隔离环境；
- 实机证据：绑定 Windows build、架构、目标软件版本和原始日志；
- 发行证据：绑定最终资产摘要、BOM、许可和发布修订。

同一证据不得跨类型冒充另一类型；“最新研究”也不能自动替代产品版本/设备上的实测证据。

## 4. 幂等、重放、重试和结果归属

### 观察

- 目录应用、软件安装和软件优化已有快照、失败重试和不改写旧批次的局部规则（如 [issues/03](issues/03-software-driver-catalog-lifecycle.md)、[issues/08](issues/08-installation-batch-runner.md)、[spec.md:942-958](spec.md)），但没有统一的操作身份、重放判定和提交点。
- `RUN-06/07`、`OPT-44`、`RST` 相关规则区分了待确认、重试和恢复，却没有对“同一请求被 UI 重发、进程重启后重复提交、安装器已完成但回调丢失”给出横切答案。
- Q17 已指出第三方安装器可能启动子进程、服务、驱动或在首进程退出后继续产生效果；若没有完成信号和 operation id，执行器会把未知状态误标为失败或重复执行。

### 横切附录应冻结

每个改变系统或目录事实的用例都必须定义：

- 稳定 `operation_id`/`batch_id` 和尝试编号；
- 可安全重放的只读检测与不可重放的副作用步骤；
- 提交点、结果检测点和回调/重启丢失后的恢复查询；
- 用户重试是结束旧记录后创建新批次，还是继续同一尝试；
- `success`、`failed`、`cancelled`、`result-unknown`、`partial/not-executed` 的互斥条件；
- 安装器/优化器返回成功但目标状态未达成时的分层结果；
- 重试前必须重新读取当前目录、版本、紧急阻止和依赖，不得重用过时规则。

幂等只适用于明确声明的操作；不能因为文件替换、进程退出码或用户点击次数相同就推断安全重放。

## 5. 并发、锁和跨实例/重启边界

### 观察

- `RUN-05`、`OPT-52` 以及事项 02 要求同一设备同一时间只有一个活动或待处理批次，但目录编辑草稿、来源手动交接、缓存写入、自更新和安全撤回通知的并发边界不同。
- 事项 07 只要求临时文件/完成标记保护并发读取；[ADR-0013](../../docs/adr/0013-software-package-cache-retention.md) 将缓存视为可清理层，但没有统一跨进程锁、租约失效和跨主机限制。
- 事项 21/22 的发行门禁、事项 17 的更新和 Q19 的活动批次互斥尚未在同一关系表中冻结。

### 横切附录应冻结

至少分别记录以下锁域，禁止用一个全局“忙”状态替代：

| 锁域 | 最小范围 | 重启/崩溃后处理 |
| --- | --- | --- |
| 设备批次锁 | 安装/系统设置/软件优化活动与待恢复批次 | 按恢复记录和租约判断，禁止新副作用直到用户继续/取消 |
| 目录写锁 | 当前有效目录、已保存草稿、恢复内容的原子提交 | 保留旧代，孤儿临时文件只读诊断后清理 |
| 缓存对象锁 | 单一资产摘要/临时下载 | 完成标记后可读；半成品不可消费；跨主机并发首版不保证 |
| 更新锁 | 应用版本替换与启动健康检查 | 活动批次或重启屏障时阻止；回退/健康超时需保留证据 |
| 安全通知锁 | 撤回/解除通知修订 | 旧修订不可覆盖新修订，离线使用上次可信结果并显式标时效 |

锁必须有持有者、取得/释放点、超时或租约、异常退出后的判定和用户可见结果。文件锁、进程退出或 UI 禁用按钮不能单独构成跨实例保证。

## 6. 时间、顺序和检查点

### 观察

- 日志要求稳定事件顺序和时间（事项 02、15），检查点最大丢失窗口仍在 Q5e；重启屏障、应用失活、批次结果检测和证据保存对时间顺序有隐含要求。
- 当前没有统一的时钟来源、时间精度、时区、单调顺序和“最后可信状态”定义；墙上时钟回拨会让日志排序、证据新鲜度和撤回通知比较产生歧义。

### 横切附录应冻结

业务事件应至少同时记录单调序号或单调时钟、UTC 时间戳和本地显示时间；跨进程/重启恢复使用持久化事件序号，不依赖墙钟排序。测试注入固定时钟和故障时间点，明确“观察到”“提交”“落盘”“可恢复”四个时刻。检查点、锁租约、健康超时和证据 freshness 使用单调时钟；公开文案使用明确时区的 UTC/本地转换。

## 06:43 状态合同反向收口

领域词汇复核后，四类状态风险已进一步映射为横切检查项，仍不新增根问题：

| 横切合同 | 最小唯一事实 | 失败关闭要求 |
| --- | --- | --- |
| 驱动/外部交接 | `handoff_id`、目标身份、主体、外部结果来源、重启/恢复 ID、观察时间 | 无返回、陈旧外部进程、用户口述或重启后未复核不得生成工作台完成事实 |
| 流程聚合 | `flow_id`、项级状态/操作结果、聚合规则版本、阻塞/续接原因 | 总结展示、全跳过、外部识别、待确认或待重启不得无条件成为成功终态 |
| 目录保存/应用/导入 | `operation_id`、候选修订/摘要、运行时校验、发布门禁、本机试用身份、提交结果 | 运行时/安全失败保留旧目录；本机应用不得改发布结论；提交未知禁止继续用新目录 |
| 软件手动交接 | `handoff_id`、软件稳定标识、解析失败、主动重检时间线、继续事件 | 外部安装已识别只更新存在事实，不创建/改写工作台安装批次或自动解锁后续动作 |

这些字段建议作为 owner/consumer/verification 映射的最小粒度；在正式模式、状态枚举和证据 ID 冻结前，不能把本表当成实现接口。
