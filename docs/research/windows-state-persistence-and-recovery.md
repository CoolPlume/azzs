# Windows 状态持久化与恢复合同研究

- 状态：研究结论与候选合同，尚未形成 ADR 或规格决定
- 研究日期：2026-08-10（北京时间）
- 适用范围：未打包自包含便携版、传统安装版、设备级与用户级状态、异常恢复、并发与卸载保留
- 项目快照：只读核对 ADR-0004、ADR-0007、ADR-0013、ADR-0014、主规格及事项 02、03、12、15、18、31、32
- 来源边界：只采用 Microsoft Learn、Windows SDK、Windows App SDK 和 Windows Installer 官方文档；通过 `agent-reach` 的 Jina Reader 读取。Exa 在本次环境中不可用，未用博客、论坛或问答补空白。

本文不选择界面呈现，不决定未保存修改的提示方式，不修改现有规格、ADR 或事项，也不把候选目录名、ACL、恢复频率或兼容窗口写成已经确认的实现。

## 1. P0 结论

### P0-1：设备级不等于所有 Windows 用户共享一份无归属状态

`FOLDERID_ProgramData` 是公共设备位置，`FOLDERID_LocalAppData` 是当前用户位置；Windows 的访问控制实际由访问令牌中的 SID 与对象 DACL 决定。[M01][M02][M05][M06][M07] 现有合同要求恢复记录、批次、草稿、日志和来源交接都进入设备级位置，却没有定义：

- 哪些记录是全机唯一事实；
- 哪些记录属于某个 Windows 用户 SID；
- 谁可以读取、修改、导出或删除另一个用户的记录；
- HKCU 设置恢复记录的目标用户 SID；
- 标准用户输入另一名管理员凭据完成 UAC 提权时，逻辑用户到底是谁。

这不是目录命名细节。若不先定义，工作台可能用管理员凭据账户的 `%LocalAppData%`、DPAPI 用户密钥或 HKCU 上下文保存和恢复本应属于登录用户的状态。UAC 官方说明标准用户会通过另一管理员的有效凭据取得管理员访问令牌；访问令牌携带用户与组 SID。[M06][M09] 项目必须先明确支持的身份模型。

### P0-2：“保存成功后即使断电也至少恢复该版本”超出了 Windows 可无条件保证的边界

Windows 默认采用写回缓存；突然断电发生在刷新前时，缓存数据会丢失。[M12] `FlushFileBuffers` 会把指定文件的缓冲信息写到设备，`FILE_FLAG_WRITE_THROUGH` 可以请求立即写盘，二者都能显著收紧丢失窗口。[M13][M14] 但微软同时明确说明并非所有硬盘硬件都支持把本地硬件缓存写穿到持久介质。[M14]

因此项目可以把“保存成功”的合同收紧到“临时文件完整写入、刷新、替换、重新打开并校验成功后才返回”，但不能把任意硬件、文件系统、存储驱动、突然断电乃至介质故障下的绝对持久性当成 Windows API 已保证事实。当前 `CAT-51`、`DBG-10` 及事项 02、03、31、32 的断电措辞需要明确其平台保证边界或支持介质前提。

### P0-3：Windows App SDK `AppInstance` 不能单独满足跨版本、跨用户、便携版与安装版共享互斥

WinUI 应用默认允许多实例。Windows App SDK `AppInstance` 可以注册键并重定向激活，但官方明确说明不同应用版本以及不同用户各自维护独立实例列表。[M18][M19] 现有合同又要求应用版本切换读取同一状态，并要求同一设备所有工作台实例共享活动批次占用。

因此 `AppInstance` 最多适合作为同一应用身份范围内的激活重定向层，不能作为设备级批次锁或持久化提交锁的唯一实现。设备级并发还需要位于稳定、受 ACL 保护的位置上的文件锁，或经过安全描述符保护的全局同步对象；崩溃后取得废弃互斥量时还必须先验证持久状态一致性。[M20][M21][M22][M23][M31]

### P0-4：应用回退、应用版本切换与状态模式迁移尚未形成闭合合同

主规格只为目录定义了 `schema_version`，没有为设备状态、历史、草稿恢复、偏好、缓存索引和日志索引定义各自模式。与此同时，项目要求：

- 便携版、安装版和应用版本切换读取同一状态；
- 新版启动失败时恢复上一应用版本；
- 应用更新和回退不得删除或改写设备状态；
- 未知目录模式安全拒绝。

若新版把设备状态单向迁移到旧版无法理解的模式，“恢复上一二进制”仍会得到无法读取或误写的状态。Windows 的应用数据版本文档也把格式变更视为显式、顺序递增的迁移工作，而不是文件解析器自动处理的事情。[M04][M26] 在确定至少一个兼容窗口、未知新模式行为和迁移回退方案前，不能声称应用回退已经安全闭合。

### P0-5：卸载保留只确认了恢复记录，尚未覆盖全部状态类别

ADR-0004 明确卸载安装版不删除恢复记录，ADR-0014 又要求日志默认永久保留；但当前没有一张完整矩阵说明历史、待恢复批次、来源交接、紧急撤回信息、当前目录、草稿、未保存恢复点、偏好、缓存和日志在卸载、重装、删除便携目录时分别如何处理。

Windows Installer 会删除自己安装且组件进入移除状态的文件，也可以通过 `RemoveFile` 表显式删除安装器未安装的文件；`Permanent` 组件则不会在卸载时删除。[M27][M28][M29] 所以“MSI 默认会替项目保留应用数据”不是可依赖事实。安装包必须按项目矩阵明确编写并验证，不能用安装器默认行为代替产品合同。

## 2. P1 结论

这些问题不一定阻止继续细化界面和目录内容，但必须在对应模块实现前闭合。

### P1-1：共享缓存没有定义是同机多实例还是多台设备并发

`CACHE-13` 允许多个工作台实例共享同一缓存位置，`CACHE-09` 又允许网络共享路径。若“多个实例”包含多台电脑，本机 `Global\` 互斥量、`AppInstance` 和 ProgramData 锁文件都不能协调另一台电脑。首版需要明确只保证同机并发，还是为 SMB 上的跨主机锁、完成标记、断线恢复和时钟无关冲突处理建立单独合同。

### P1-2：永久日志缺少磁盘耗尽、并发清空与关键状态隔离合同

ADR-0014 要求日志默认永久保留，规格允许立即清空，但没有定义日志占满磁盘时权威状态保存是否仍能失败关闭、活跃写入期间清空的原子边界、清空后事件序号如何继续，以及日志索引损坏是否影响恢复记录。日志与恢复记录在逻辑和存储上都要隔离；普通日志写入失败必须形成可观察缺口，但不能把未落盘日志当成阻止权威状态提交的前置条件。

### P1-3：未保存恢复没有可测试的最大丢失窗口与冲突生命周期

现有合同正确地把“恢复的未保存修改”与已保存草稿、当前目录分开，但明确不决定恢复写入频率。若没有最大丢失窗口或必触发检查点集合，断电后的“尽量找回”无法稳定验收；若没有基础草稿代次、恢复会话墓碑和冲突规则，正常放弃、旧检查点复现及保存后再次编辑容易互相覆盖。

### P1-4：日志与状态测试门禁尚未覆盖真实平台故障阶段

事项 31 已要求无界面核心测试，但持久化适配器仍需覆盖 ACL、两个 Windows 用户、跨版本未知模式、废弃锁、磁盘已满、只读介质、替换部分完成布局和提交各阶段强制终止。进程终止测试不能代替虚拟机硬断电或受支持存储介质上的实机故障注入；二者应形成不同证据。

## 3. Microsoft 官方事实

本节只记录官方资料明确说明的行为，不包含项目选择。

### 3.1 已知文件夹与未打包应用

1. 新的 Win32 代码应使用 `SHGetKnownFolderPath` 与 `KNOWNFOLDERID`，而不是硬编码环境变量或旧 CSIDL。已知文件夹可以被重定向到其他位置，甚至网络位置。[M01][M03]
2. `FOLDERID_ProgramData` 的类型是固定公共位置，默认路径为 `%ProgramData%`；`FOLDERID_LocalAppData` 的类型是每用户位置，默认路径为 `%USERPROFILE%\AppData\Local`。[M02]
3. `SHGetKnownFolderPath` 的用户令牌为 `NULL` 时取得当前用户的文件夹。要取得另一用户的文件夹，需要该用户令牌、相应令牌权限，并且该用户注册表配置单元已经装载。[M03]
4. `Windows.Storage.ApplicationData.Current` 提供的是与应用包关联的应用数据存储。[M04] 当前候选发行是未打包便携目录和传统安装器，不能在没有包身份验证的前提下把该包存储当成跨发行形态的设备状态根。
5. 便携版可执行文件所在目录和传统安装版的程序目录不是 Windows 定义的共享应用数据位置。两种发行形态只有使用同一个稳定 Known Folder 根，才会自然落到同一物理状态树。

### 3.2 SID、访问令牌与 ACL

1. Windows 登录后为用户创建访问令牌；令牌包含用户账户和组账户 SID。进程访问安全对象时，系统用令牌与对象安全描述符作访问判断。[M06][M08]
2. 对象 DACL 中的 ACE 决定哪些 SID 被允许或拒绝访问；没有 DACL 的对象允许所有人完全访问，空 DACL 则不允许任何人访问。[M07]
3. `CreateDirectory` 没有接收显式安全描述符时，目录默认 ACL 从父目录继承。[M05] 因而“路径位于 ProgramData”本身不等于已经获得适合该应用的最小权限。
4. UAC 下管理员登录会有标准和管理员两个访问令牌；标准用户要运行需要管理员令牌的应用时，需要提供有效管理员凭据。[M09] 项目不能从“进程已提权”推断“进程令牌 SID仍是发起操作的标准用户”。
5. `GetTokenInformation(TokenUser)` 可以取得令牌对应的用户账户。[M08] 但“哪个令牌代表业务上的用户”仍由应用架构决定。

### 3.3 DPAPI 的作用与边界

1. `CryptProtectData` 默认通常只有具有相同登录凭据的用户才能解密，并且通常要求在同一台电脑上解密。[M10]
2. 使用 `CRYPTPROTECT_LOCAL_MACHINE` 后，保护范围改为电脑；该电脑上的任何用户都可以调用 `CryptUnprotectData` 解密。[M10]
3. DPAPI 会为密文添加 MAC 完整性检查，但当前 `CryptUnprotectData` 官方文档仍警告：损坏时可能返回不同错误，某些情况下甚至可能成功返回损坏输出；稳健的防篡改仍应增加应用级完整性检查。[M10][M11]
4. DPAPI 解决的是敏感字节保护，不定义文件 ACL、并发写入、原子替换、模式迁移或损坏回退。机器范围 DPAPI 也不隔离同机用户。

### 3.4 文件替换、刷新与断电

1. Windows 默认先把写入放进系统文件缓存；缓存尚未刷新时突然断电会丢失数据。文件系统元数据也会被缓存。[M12]
2. `FlushFileBuffers` 把指定文件的缓冲信息写到设备。频繁调用有性能代价；微软对需要确保关键数据写入持久介质的高频场景提到无缓冲与写穿 I/O。[M13]
3. `FILE_FLAG_WRITE_THROUGH` 会使数据不延迟刷新；与 `FILE_FLAG_NO_BUFFERING` 一起使用时，系统还会请求把硬盘本地硬件缓存写穿到持久介质，但并非所有硬件都支持这一能力。[M14]
4. `ReplaceFile` 把新文件替换到旧文件名，并可创建旧文件备份；替换、备份和被替换文件必须位于同一卷。[M15]
5. `REPLACEFILE_WRITE_THROUGH` 当前明确标为不支持。`ReplaceFile` 文档还列出了失败后旧文件可能不再位于原名称、替换文件仍在原名称或继承部分属性等多种结果。[M15]
6. `MoveFileEx(MOVEFILE_WRITE_THROUGH)` 不会在移动实际写盘前返回，并保证以复制加删除完成的移动在返回前刷新；跨卷移动不保留原安全描述符。[M16]
7. Microsoft 不建议新项目依赖 Transactional NTFS。对单个文档式文件，官方给出的常见替代是先写新文件，再用 `ReplaceFile` 替换；对结构化数据则建议使用支持事务的数据存储。[M17]

### 3.5 进程、实例与互斥

1. WinUI 应用默认是多实例；Windows App SDK `FindOrRegisterForKey` 会返回第一个注册某个键的应用实例，可用于激活重定向。[M18][M19]
2. Windows App SDK 为不同应用版本和不同用户维护分开的实例列表；进程终止时键会自动注销，但退出与重定向之间仍可能有竞争条件。[M18]
3. Windows 命名内核对象默认按会话分区；`Global\` 前缀可以创建跨会话对象，`Local\` 明确使用当前会话命名空间。[M20]
4. 创建命名互斥量时可提供安全描述符；若不提供，其 ACL 来自创建者主令牌或模拟令牌的默认 DACL。[M21]
5. Microsoft 明确警告固定名称的单实例互斥量可能被恶意用户预先创建，从而阻止应用启动；官方建议随机名称并保护名称，或使用锁定文件。[M21]
6. 互斥量所有者线程终止而未释放时，下一等待者会收到 `WAIT_ABANDONED`。官方要求：若互斥量保护持久状态，应检查该状态的一致性；废弃锁不能被解释为上一个操作已经成功。[M22][M23]
7. `CreateFile` 使用零共享模式成功打开文件后，在句柄关闭前其他冲突打开会失败；`LockFileEx` 的锁在进程终止或句柄关闭后由系统解除。[M14][M31]

### 3.6 崩溃恢复与未保存内容

1. `RegisterApplicationRecoveryCallback` 可以在未处理异常或应用无响应时让 WER 调用恢复回调；回调需要在约定间隔内报告仍在恢复，否则 WER 终止恢复。[M24]
2. Microsoft 建议应用周期性保存数据和状态，以缩短恢复工作和丢失窗口。[M24]
3. 该回调只覆盖 WER 能介入的异常或无响应场景，不会在物理断电后补执行。断电恢复必须依赖断电前已经落盘的检查点。
4. `RegisterApplicationRestart` 在崩溃或无响应时只向用户提供重启机会，不会在没有用户同意时自动重启；为避免循环，进程至少运行 60 秒才会被重启。[M25]
5. 因此“保存的草稿持久化”“未保存修改检查点”和“崩溃后是否重新启动应用”是三个不同合同，不能由一个恢复 API 同时替代。

### 3.7 模式版本与 Windows Installer

1. Microsoft 的应用数据版本指导要求应用在格式变化时检查存储版本、按顺序递增版本迁移，并在成功迁移后更新版本号。[M26] 该 API 绑定包应用数据，本项目只能借鉴版本语义，不能据此声称未打包状态迁移已经实现。[M04]
2. Windows Installer 的 `RemoveFiles` 会删除 `InstallFiles` 安装且对应组件进入移除状态的文件；`RemoveFile` 表还能删除安装器作者指定的其他文件或空目录。[M27][M28]
3. 组件设置 `msidbComponentAttributesPermanent` 后，Windows Installer 不会在卸载时移除该组件。[M29]
4. `ALLUSERS` 决定安装包是每用户还是每机上下文；这会影响安装目录和注册表位置，但不自动决定应用运行时数据应否在用户间共享。[M30]

## 4. 项目合同建议

本节是从官方事实推导出的候选合同，不代表维护者已经确认。建议后续由规格、ADR 和事项各自拥有相应部分，避免在多份文档中复制实现细节。

### 4.1 建议的状态分区

以 `SHGetKnownFolderPath(FOLDERID_ProgramData)` 解析出的稳定产品根作为便携版与安装版共享入口，产品根不包含应用版本、发行形态或处理器架构。候选逻辑分区如下：

| 状态类别 | 候选根与归属 | 原因 | 不应混入 |
| --- | --- | --- | --- |
| 全机权威状态 | `ProgramData/<vendor>/<product>/machine/` | 跨便携/安装、版本、架构和 Windows 重启共享 | 用户偏好、未脱敏用户私有内容 |
| 按用户隔离的设备状态 | `ProgramData/<vendor>/<product>/users/<owner-sid>/` | 仍位于设备根，但显式保留 SID 归属与 ACL | 依赖当前进程 `%LocalAppData%` 的隐式身份 |
| 每用户非权威界面缓存 | `FOLDERID_LocalAppData/<vendor>/<product>/` | 可重建、无需跨用户共享 | 恢复记录、批次、历史、当前目录、唯一草稿 |
| 软件包缓存载荷 | 默认设备缓存根或用户选择位置 | 满足 ADR-0013 与可移动/网络位置 | 唯一缓存索引、恢复记录和安全策略 |
| 程序文件 | 便携目录或安装目录 | 可替换、可删除的应用二进制 | 任何必须跨版本或卸载保留的业务状态 |

对现有状态，候选归属应进一步明确：

| 记录 | 候选业务归属 | 必须携带的身份事实 |
| --- | --- | --- |
| 系统设置恢复记录 | 全机索引，记录实际作用域 | 设置稳定标识、作用域、目标 SID（如属 HKCU）、写入前值、执行快照 |
| 推荐流程、安装/优化批次、待恢复状态 | 全机 | 稳定记录 ID、创建者 SID、状态代次、占用租约/运行 ID |
| 来源手动交接与未完成列表 | 至少按创建者 SID 分区；是否全机可见待决定 | 软件稳定标识、创建者 SID、状态与历史事件 |
| 当前有效目录和紧急撤回信息 | 全机 | 模式、修订、内容身份、应用关联 ID、最后可信代次 |
| 已保存未应用草稿 | 按维护者 SID | 草稿 ID、所有者 SID、基础目录身份、保存代次 |
| 恢复的未保存修改 | 按维护者 SID，独立于已保存草稿 | 编辑会话 ID、基础草稿代次、检查点代次、仍未保存标志 |
| 历史 | 全机记录，读取权限待定 | 原始创建者 SID 的匿名稳定引用、不可变事件序号 |
| 日志 | 按运行/用户分片并有全机索引 | 运行 ID、写入者 SID、格式版本、最后成功刷新点 |
| 视图与调试偏好 | 每用户 | 偏好所有者 SID；不得改变全机业务状态 |

这里的 `<owner-sid>` 是逻辑标识，不要求把原始 SID 暴露到日志或导出文件；诊断导出仍应按现有脱敏合同替换为本次文件内匿名标识。

### 4.2 身份与 ACL 候选合同

1. 在读取或写入任何按用户记录前，核心先取得一个明确的“状态主体”，并把其 SID 作为类型化值交给持久化适配器；适配器不能自行把“当前进程令牌”解释成状态主体。
2. 产品根创建时使用项目定义的安全描述符，不依赖父目录默认继承就宣称隔离完成。至少分别定义 SYSTEM、本机 Administrators、记录所有者 SID和普通已认证用户的读取、写入、删除、改 ACL 权限。
3. 全机可写目录不得向普通用户授予可替换状态文件、锁文件或目录本身的权限；否则常驻管理员进程会把低权限用户提供的内容当成高权限状态。
4. 每用户目录应由所有者 SID、SYSTEM 和受信任管理员主体访问；是否允许其他本机管理员读取包含设备上下文的日志，属于需要明确披露的产品决定。
5. 状态文件的所有者 SID是业务数据的一部分，DACL是系统执行边界；两者必须同时检查，不能互相替代。
6. DPAPI 只保护不可避免的秘密字段。项目当前目标是不保存口令、Cookie、令牌和敏感 URL；若没有秘密，不应为普通状态整体套 DPAPI。机器范围 DPAPI不能代替 SID ACL，用户范围 DPAPI又会影响跨用户和替代凭据提权场景。
7. ACL 布局本身应有版本，并在持久化根初始化或升级时验证。修复 ACL必须在设备级独占锁下完成并留下安全事件，不能在每次文件打开失败后静默放宽权限。
8. 文件信封中的普通非密钥摘要只能发现意外损坏，不能阻止能够同时改写载荷和摘要的主体伪造内容。若威胁模型要求抵抗恶意篡改，需要另行决定带密钥认证、密钥归属与轮换；不能只因使用 SHA-256 一类摘要就宣称“防篡改”。

### 4.3 单个权威聚合的候选提交协议

对当前目录、已保存草稿、批次状态、恢复记录等“保存成功即成为权威事实”的聚合，建议使用相同的持久化合同：

1. 取得设备级提交锁；锁的名称或文件路径来自稳定产品身份，不包含应用版本或发行形态。
2. 读取并验证当前代次，确认调用者提供的预期代次仍是当前代次，防止旧实例覆盖新实例。
3. 在目标文件同一目录、同一卷写入全新的临时文件。文件信封至少包含记录类型、状态模式版本、单调代次、事务 ID、写入应用版本、所有者/作用域、载荷长度和应用级完整性摘要。
4. 完整序列化后重新读取内存或临时文件，执行语法、模式、跨字段不变量和摘要校验。
5. 对临时文件调用 `FlushFileBuffers`；失败即返回保存失败，不能显示“已保存”。
6. 关闭临时文件句柄，用 `ReplaceFile` 在同卷替换当前文件并保留上一代备份。第一次创建可用 `MoveFileEx` 的写穿选项完成命名提交。
7. 按 API 错误码处理 `ReplaceFile` 的所有部分完成布局；不能假定失败时旧文件一定仍在原名。
8. 重新打开当前文件，验证代次、模式、载荷和摘要；成功后才向核心报告提交完成。
9. 保留至少一个经过验证的上一代，不在同一提交中急于删除所有回退证据。
10. 日志记录事务 ID、预期/实际代次、刷新结果、替换结果、验证结果和最后可信代次，但不把“日志已写”当成状态提交成功。

`REPLACEFILE_WRITE_THROUGH` 不受支持，因此不能用该标志伪造耐久性保证。[M15] 对多个文件的跨聚合更新，不应把一串 `ReplaceFile` 宣称为单一原子事务；要么把必须一致的事实收进同一聚合，要么使用显式预写日志/事务型存储和可恢复状态机。不要新依赖 TxF。[M17]

### 4.4 保存、日志与外部效果的不同耐久等级

建议用合同名称区分至少三类写入：

| 等级 | 例子 | 返回成功前要求 |
| --- | --- | --- |
| 权威提交 | 保存草稿、应用目录、建立重启屏障、更新恢复记录、结束/取消批次 | 完整验证、刷新、替换、重新读取校验 |
| 恢复检查点 | 未保存修改自动检查点、执行中进度心跳 | 不提升业务状态；失败可报告但不能污染已保存代次 |
| 诊断追加 | 普通/调试日志事件 | 按风险节点刷新；精确记录最后成功落盘点与未知区间 |

外部系统效果和本地状态无法靠普通文件替换形成一个跨注册表、安装器或第三方进程的原子事务。执行合同应把每个风险操作建模为“意图已持久化、效果可能发生、效果已观察、结果已确认”等可恢复阶段。若进程在外部效果后、结果落盘前退出，应进入“结果待确认”并重新检测，而不是依赖没有出现成功日志来重跑。现有规格的待确认语义与此方向一致。

### 4.5 损坏与部分替换回退

启动时应在设备级锁下扫描当前、上一代备份和已知事务残留，并按文件内部的记录类型、事务 ID和代次判断，而不是只按文件名或修改时间判断：

1. 当前文件完整有效：加载当前代次，清理已确认无用的旧临时文件。
2. 当前无效、上一代有效：恢复上一代为“最后可信状态”，记录损坏事件；不能把恢复动作伪装成最新提交成功。
3. 当前缺失、替换文件有效且事务证据证明提交完成：完成命名恢复并重新校验。
4. 只有未完成临时文件：不得自动把它提升为已保存草稿、当前目录或已完成批次。
5. 当前和备份都无效：禁止新的修改操作，保留原字节和诊断证据，提供显式恢复/重新初始化路径；历史、日志或其他独立聚合能安全读取时继续只读可用。
6. DPAPI 解密成功后仍执行项目摘要与模式校验，因为官方明确警告损坏输出存在成功返回的可能。[M11]

### 4.6 跨实例候选合同

建议把实例协调拆成两个层次：

- `AppInstance`：同一 Windows App SDK 应用身份范围内处理第二次启动和激活参数重定向；它不拥有设备批次状态。
- 设备级锁与占用记录：跨便携/安装、x64/ARM64、应用版本、用户和 Windows 会话协调状态提交及批次占用。

设备级锁优先候选是受 ACL 保护的 ProgramData 锁文件：以零共享模式或 `LockFileEx` 保持句柄，并把运行 ID、进程 ID、应用版本和状态代次作为诊断元数据写入另一个可校验记录。文件是否仍存在不能代表锁是否仍被持有；实际句柄锁才是互斥事实。[M14][M31]

若采用 `Global\` 命名互斥量，必须提供显式安全描述符并处理恶意预创建；收到 `WAIT_ABANDONED` 时，先把受保护聚合视为一致性未知并执行恢复扫描，不得直接继续批次。[M20][M21][M22][M23]

活动批次占用状态还应持久化，不能只存在于互斥量。进程退出会释放锁，但“批次等待确认、等待重启或待恢复”按产品语义仍占用设备；新实例必须从权威状态判断是进入既有批次、只读验证，还是允许新建批次。

`CACHE-13` 还需要区分同一设备多个实例和多台设备同时使用同一网络共享。设备级全局互斥只能保护本机；若合同要覆盖多台电脑，共享缓存目录本身还需要跨主机文件锁、完成标记和冲突命名策略。

### 4.7 未保存修改恢复候选合同

未保存恢复文件必须是一个独立状态类型，不能复用已保存草稿文件或当前目录文件：

1. 每个检查点记录编辑会话 ID、所有者 SID、基础已保存草稿 ID与代次、当前有效目录身份、检查点代次、应用版本和“仍未保存”标记。
2. 周期性/防抖检查点是断电恢复的主要证据；WER 恢复回调只能在可用时补一次最佳努力刷新，不能替代检查点。[M24]
3. 检查点写入失败不损坏已保存草稿，也不生成“恢复成功”事实。
4. 下次启动只在检查点完整、模式受支持、所有者匹配且基础代次仍可解释时生成“恢复的未保存修改”。基础代次冲突时返回类型化冲突，不自动合并、保存或应用。
5. 显式保存恢复内容时，用权威提交协议生成新的“已保存未应用”草稿，然后提交一个已消费/清除恢复会话的状态转换；任一步骤失败都保留此前已保存版本。
6. 显式放弃时先持久化该恢复会话的墓碑/已放弃代次，再尽力删除载荷，避免删除失败使旧检查点下次重新出现。
7. 正常关闭时用户选择放弃未保存修改，也应使对应编辑会话检查点失效，不能把正常放弃在下一次启动误判为崩溃恢复。

恢复写入频率和启动呈现仍可保留为实现/界面决定，但验收至少要定义一个可测的最大丢失窗口或触发集合，否则“尽量找回”无法形成稳定测试证据。

### 4.8 状态模式与应用回退候选合同

建议把下列版本明确分开，不复用一个 `schema_version`：

- 设备状态存储模式；
- 每类目录模式；
- 日志事件模式与诊断导出格式；
- 未保存恢复检查点模式；
- 缓存索引模式；
- 单个业务快照中冻结的目录版本。

迁移候选规则：

1. 模式使用顺序递增整数；文件信封还记录最小读取版本和最小写入版本。
2. 未知更高模式一律禁止写入、降级或清空；可识别的独立日志/历史保持只读。
3. 迁移只在设备级提交锁下执行，先复制旧代次，再对副本逐步迁移、验证全部不变量，最后以权威提交协议切换。
4. 每一步迁移是可重复或有明确已完成标记的；异常退出后可以从旧代次重新开始，不能半迁移原文件。
5. 当前有活动、等待确认、等待重启或待恢复批次时，迁移必须证明该状态也能无损迁移；否则阻止新版进入可修改模式。
6. 新版至少要保留上一应用版本可读取的状态，或保留能让上一版本恢复的兼容快照。支持窗口由维护者决定并写入更新/回退 ADR。
7. 旧版遇到新模式时必须保留字节、拒绝修改并给出准确原因；不得把“未知”当成首次运行后初始化空状态。

### 4.9 安装、卸载与便携删除候选合同

建议先确定数据所有权，再编写安装器：

| 数据 | 卸载安装版候选行为 | 删除便携目录后的候选行为 | 当前依据/缺口 |
| --- | --- | --- | --- |
| 安装目录内应用文件 | 删除 | 随目录删除 | 安装器拥有 |
| 设备恢复记录 | 保留 | 保留 | ADR-0004 已确认 |
| 待恢复状态与只读历史 | 保留 | 保留 | 否则破坏恢复语义；需正式确认 |
| 当前有效目录与紧急撤回信息 | 保留 | 保留 | 支持重装/切换；需正式确认 |
| 日志与诊断索引 | 默认保留 | 保留 | ADR-0014 默认永久；是否卸载视为清空待确认 |
| 已保存草稿与未保存恢复点 | 待决定 | 保留在设备根 | 涉及用户内容和隐私 |
| 缓存载荷 | 待决定 | 保留到期限或主动清理 | 卸载后没有进程执行 7 天清理 |
| 每用户偏好 | 待决定 | 保留 | 对重装便利与残留最小化取舍 |

若使用 MSI：

- 应用运行时创建的数据不要作为普通安装文件组件拥有；
- 不要用指向状态根的通配 `RemoveFile`；
- 若安装器负责创建带 ACL 的 ProgramData 根，必须验证卸载后目录和 ACL 在有状态、空状态、升级、修复时的行为；
- `Permanent` 组件可以保留安装器组件，但是否用它拥有状态根需要结合组件引用计数、修复和升级实测，不应因名称直观而直接采用；
- 安装器提供的“删除本机数据”若存在，必须复用应用的待恢复/恢复记录保护规则，不能成为绕过 `SET-13` 的第二删除入口。

便携版没有操作系统卸载动作。若用户只删除便携目录，ProgramData 状态仍会保留；项目需要把“删除程序文件”和“明确清理本机数据”视为不同动作，但具体入口与文案不在本文决定。

## 6. 维护者决策树（明早答题）

这些是产品决定，不能从 Microsoft 文档推出。应先回答第一轮全部根问题，再按答案重算后续分支；以下推荐只是首版默认值，不是已确认合同。在形成共享理解前，不应把候选答案写回规格、ADR 或事项。

### 待确认领域词汇

以下词汇只在本文中帮助拆开身份与耐久语义，尚未写入 `CONTEXT.md`：

- **交互用户**：发起工作台启动、拥有当前交互式桌面会话的 Windows 用户。
- **执行主体**：Windows 实际用于访问检查的进程或线程访问令牌中的用户 SID；替代凭据提权时可能不同于交互用户。
- **状态主体**：某份按用户状态在产品语义上归属的 SID。它必须由核心显式确定，不能由持久化适配器直接等同于执行主体。
- **设备级状态**：存放在稳定设备根并跨发行形态、应用和 Windows 重启保留的状态；该词只描述生命周期，不自动表示所有 Windows 用户都可读写。
- **权威提交**：成功后改变产品事实且允许界面显示“已保存”或对应完成状态的持久化转换。
- **恢复检查点**：只用于异常恢复、不会把未保存内容提升为已保存事实的最佳努力持久化副本。
- **最后可信代次**：最近一次完成完整性、模式和业务不变量校验并可安全载入的状态代次，不等同于文件修改时间最新者。

### 第一轮：可立即回答的根决定

❓ **STATE-D1** - **首版支持哪种 Windows 用户身份模型？** 当前架构是单进程常驻管理员会话。是只支持登录用户用自己的拆分管理员令牌提权，还是支持标准用户输入另一名管理员凭据后仍把交互用户视为状态主体？

➡️ 推荐：首版只支持前者。启动时检测交互会话用户与提权令牌用户是否一致，不一致则准确阻止并说明；后者需要未提权前端/提权代理、显式传递目标 SID 和 HKCU 目标，不应在单进程里隐式猜测。

❓ **STATE-D2** - **权威状态支持哪些存储介质，断电承诺到哪里？** 设备状态根是否只支持本机系统卷，还是也允许网络共享、U 盘或其他移动介质？“保存成功”是否仍承诺任意硬件下物理断电后绝对恢复？

➡️ 推荐：权威状态只位于本机 `ProgramData` 根；网络与移动位置只用于软件包缓存。保存成功必须完成项目定义的刷新、替换和重新校验，但物理断电保证明确受 Windows、文件系统、驱动和硬件兑现刷新请求的边界约束；无条件保证进程崩溃一致性，不对任意介质作绝对耐久性承诺。

❓ **STATE-D3** - **应用版本切换支持多宽？** 是支持发布回退链中的当前版与上一版，还是允许用户任意启动很旧的便携版并读写同一状态？

➡️ 推荐：首版只保证发布链 N 与 N-1，不承诺任意旧便携版。未知更高状态模式的旧版本只读拒绝，绝不初始化、降级或写回；发布门禁必须证明自动回退覆盖既定 N-1 窗口。

❓ **STATE-D4** - **共享缓存的“多个实例”是否包含多台电脑？** `CACHE-13` 与网络共享路径组合后，可能被理解为多台设备同时写同一缓存。

➡️ 推荐：首版只保证同一设备上的便携版、安装版和不同架构实例；网络共享可作为位置，但不支持多台电脑同时写。跨主机并发需要独立的 SMB 锁、断线与冲突协议，后续另立范围。

❓ **STATE-D5** - **未保存修改最多允许丢失多久？** 只有“尽量找回”无法形成稳定验收；需要时间上限或必触发检查点集合。

➡️ 推荐：首版接受最多 10 秒的编辑丢失窗口；语义编辑后防抖写入，并在达到 10 秒上限、应用失活和进入高风险操作前强制检查点。WER 回调只补充最佳努力刷新，不计作唯一保证。

### 第二轮：依赖第一轮答案

❓ **STATE-D6** - **哪些设备级记录允许跨 Windows 用户查看和操作？** 该问题依赖 STATE-D1；需要分别决定全机权威记录、用户草稿/检查点、偏好、日志、历史与诊断导出。

➡️ 推荐：恢复记录、批次、当前目录、历史和紧急撤回信息是全机权威事实；已保存草稿、未保存检查点和偏好按状态主体 SID 隔离。普通浏览与导出默认只显示当前状态主体和全机事实；跨用户诊断必须是明确的管理员操作，并继续匿名化用户标识。

❓ **STATE-D7** - **“保存成功”采用什么可测试定义？** 该问题依赖 STATE-D2；还要区分权威提交、恢复检查点和普通诊断日志。

➡️ 推荐：权威提交只有在新代次完整验证、临时文件刷新、同卷命名替换、当前文件重新打开并校验、上一可信代次仍可回退后才返回成功。替换 API 返回失败时按实际文件布局恢复，不笼统宣称“原子”；检查点和日志失败不得提升业务状态。

❓ **STATE-D8** - **状态迁移与应用回退怎样配对？** 该问题依赖 STATE-D3；二进制恢复不能与已经不可逆迁移的状态分开讨论。

➡️ 推荐：每类状态单独版本化，迁移采用设备锁下的写时复制并保留迁移前可信代次；N-1 遇到 N 模式只读拒绝。若某次迁移无法保持 N-1 兼容，该发行不得声称支持自动二进制回退，除非能证明状态快照回退不会丢失新版产生的事实或外部效果。

❓ **STATE-D9** - **检查点何时生成、冲突和放弃如何结束？** 该问题依赖 STATE-D5；需要把时间窗口变成状态机，而不是界面定时器细节。

➡️ 推荐：每个编辑会话记录基础草稿代次和单调检查点代次；语义编辑使用短防抖但不得超过 STATE-D5 上限。基础代次变化时返回冲突而不自动合并；保存或放弃先提交已消费/墓碑状态，再尽力删除旧载荷，防止旧检查点复活。

❓ **STATE-D10** - **永久日志在磁盘不足和并发清空时怎么退化？** 该问题依赖 STATE-D2 与 STATE-D6；既要遵守默认永久保留，也不能让日志目录成为恢复记录的第二所有者。

➡️ 推荐：日志、历史和恢复记录使用独立聚合与权限；清空日志提交一个明确截止事件并切换到新日志段，活跃写入继续使用新事件序号。空间不足时停止非关键日志、记录可检测的覆盖缺口并提醒用户，绝不自动删除恢复/历史；权威提交若也无法安全落盘则失败关闭，不伪报保存成功。

### 第三轮：由前两轮收口

❓ **STATE-D11** - **卸载、重装、删除便携目录和明确清理数据的完整矩阵是什么？** 该问题依赖 STATE-D6 与 STATE-D10；必须逐类决定历史、日志、当前目录、紧急撤回信息、恢复记录、草稿、检查点、偏好、默认缓存和自定义缓存。

➡️ 推荐：普通卸载和删除便携目录只删除程序文件，保留 ProgramData 中的权威状态、历史、日志、草稿与恢复证据；重装后再按既有缓存期限清理默认缓存，安装器永不递归删除用户选择的自定义缓存路径。另设明确的本机数据清理合同，区分“当前用户数据”和“全机数据”，并在活动/待恢复状态存在时阻止破坏性清理。

❓ **STATE-D12** - **哪些证据才允许宣布持久化合同完成？** 该问题依赖前面全部答案；单元测试、进程强杀、虚拟机断电、两用户 ACL、应用回退和安装器生命周期分别证明不同事情。

➡️ 推荐：把第 7 节矩阵设为实现前验收设计输入；任何不纳入支持范围的介质、用户身份或版本组合必须明确写成不支持，不能用“未测试”暗示已有保证。

## 7. 后续验证清单

这些是开始产品实现后必须建立的合同或实机证据，不表示本文已经验证通过：

- [ ] 便携版与安装版、x64 与 ARM64、当前版与上一版同时启动，证明它们竞争同一设备锁且不会覆盖新代次。
- [ ] 两个 Windows 用户与两个会话同时运行，验证全机状态、SID 分区、日志读取和删除权限。
- [ ] 标准用户用另一管理员凭据提权，记录进程 `TokenUser`、Known Folder、DPAPI、HKCU 和目标设置实际归属。
- [ ] 在写临时文件、刷新前后、替换前后、重新验证前后逐点强制终止进程，证明只加载当前或上一有效代次。
- [ ] 在支持的本地文件系统上执行虚拟机硬断电/宿主断电等实机故障注入，并把硬件与文件系统边界写进证据；模拟进程崩溃不能冒充断电测试。
- [ ] 注入当前文件损坏、备份损坏、两者同时损坏、DPAPI 成功但应用摘要失败、替换后文件名异常等路径。
- [ ] 新版迁移后启动上一版，验证既定兼容窗口；未知新模式不得初始化空状态或写回旧格式。
- [ ] 活动、等待确认、等待重启和待恢复批次中分别崩溃，证明锁释放后仍保持业务占用并先只读校验。
- [ ] 正常放弃未保存修改、崩溃、电脑断电、检查点损坏和基础草稿已变化时，恢复状态不会覆盖已保存草稿或当前目录。
- [ ] 安装、升级、修复、失败回滚、卸载、重装和只删除便携目录，逐项核对最终保留矩阵与 ACL。
- [ ] 本机磁盘、移动介质和 SMB 共享分别验证缓存锁、完成标记、介质断开和多机竞争；未纳入保证的组合明确记录为不支持。

## 9. 证据限制

- 本文是官方资料与当前文档快照的研究，不是 Windows 实机、断电、并发、ACL、安装或卸载通过记录。
- `FlushFileBuffers`、写穿和文件替换的真实耐久性仍受文件系统、驱动、硬件缓存、网络或移动介质影响；必须在项目实际支持矩阵中验证。
- 本文没有为持久化格式选择 JSON、TOML、二进制、ESE、SQLite 或其他存储技术，也没有选择 MSI、WiX 或其他传统安装器。
- 本文没有决定调试编辑器在启动时如何呈现恢复内容；只定义候选核心状态和持久化边界。
- 现有规格和事项在本研究期间存在并行编辑。后续回写前应重新核对最新版本，并由维护者回答第 6 节问题。
