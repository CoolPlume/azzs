# Windows 发布候选必须通过受信 Authenticode 签名

Status: accepted  
Date: 2026-08-25  
Supersedes: ADR-0005（仅针对发布候选的“不签名”决定）

## Context

Windows Smart App Control 和 SmartScreen 会使用 Authenticode 发布者身份、文件签名信誉及文件信誉判断未知的 Win32 程序。工作台的 0.2.0 候选是新的未签名哈希；在本机事件 3033/3077/3118 中，Explorer 在进程启动前按 `VerifiedAndReputableDesktop` 策略拒绝该文件。360 没有对应误报证据，且不能通过修改 360 设置解决这个问题。

仅修改文件名、资源版本、图标或运行时逻辑不能建立 Windows 发布者信任。自签名证书也不能作为公开发行的信任根；它只适合由测试设备预先信任的开发/验收环境。

## Decision

- 本地开发构建允许保持未签名，但必须显式传入 `-DevelopmentBuild`，不能通过正式发布打包门禁；省略开发或正式签名意图的构建与打包入口必须失败关闭。
- 便携版和安装版发布候选必须对载荷中的 `.exe`、`.dll`、`.sys`、`.msi`、`.msix` 和 `.appx` 文件执行 Authenticode 签名验证；验证状态必须严格为 `Valid`。
- 发布构建通过 `eng/build.ps1 -RequireAuthenticodeSignature` 启用门禁。证书私钥由构建环境安全注入，脚本只接受证书指纹，不把私钥写入仓库或发行目录；签名使用 SHA-256 文件摘要和 RFC 3161 时间戳。
- 签名脚本只允许调用方显式列出的、位于载荷根目录的项目自有文件进入代签；已签名的系统或第三方依赖可以保留其原有签名，任何未签名第三方载荷都必须先取得独立、可审计的签名，工作台不得代签。
- `eng/package-portable.ps1` 与 `eng/package-installer.ps1` 的正式路径必须启用同一门禁。没有可用的受信代码签名证书时，构建失败，不生成可宣称为正式发行的替代制品。
- 工作台的管理员权限、更新查询、第三方安装器边界和现有业务功能不因安全软件误报而删除或改成空实现。
- PE 链接启用 CFG、ASLR、NX 和高熵地址空间；这些缓解措施不能替代签名，也不能单独保证 Smart App Control 放行。

## Consequences

- 正式发布需要维护者提供受信代码签名证书、私钥保护和时间戳服务；当前机器没有可用项目证书，因此本次只能完成工程门禁，不能产出已签名发行 EXE。
- 签名不能证明代码没有漏洞，也不能保证 360、企业策略或每台设备的信誉结果；发布前仍须绑定实际文件、证书链和 Windows 实机证据。
- ADR-0005 关于未签名开发构建和历史资产的说明仍保留；其“长期不签名发布候选”部分不再适用。
