# Codex 总调度与执行策略

本文件是本项目多会话开发的长期调度规则。目标是尽快形成可用成品，并保持足够的工程质量、Git 可恢复性和准确证据；规划、审查与验证服务于交付，不成为交付本身。

## 1. 会话职责

### 总调度会话

- 使用 GPT-5.6 Sol Ultra。
- 负责拆分工作、确定依赖和集成顺序、选择执行模型、控制并发、处理阻断、核对关键门禁以及维护整体进度。
- 主要做统筹和与统筹直接相关的工作。实现、测试、文档收口和 Git 操作尽量交给执行会话。
- 可以直接处理很小且确定的解阻修改、冲突中的明确组合、会话中断后的状态恢复，以及分发成本高于执行成本的机械工作。
- 问题已经足够明确时直接分发，不为低影响细节持续追问维护者。

### 执行会话

- 接受一个边界清楚、可以独立交付的工作单元；能在一次会话中完成更多连续步骤时，不人为拆成多次往返。
- 默认自行完成实现、最小充分验证、提交、推送和准确交接。除非缺少会改变结果的维护者决策，不把普通续跑或工具审批交回维护者。
- 会话可以再使用子代理，但只有独立并行工作确实节省时间时才这样做。

## 2. 模型路由

按最低充分的模型与推理强度选择，并随任务阶段升降档：

| 工作类型 | 默认模型与推理强度 |
| --- | --- |
| 总调度、跨事项取舍、全局集成决策 | GPT-5.6 Sol Ultra |
| 固定 diff、日志摘取、状态核对、简单文档和其他机械工作 | GPT-5.6 Luna（仅限连通性已验证后的固定、可重复、低风险机械工作）；必要时 GPT-5.6 Terra Medium 或 High |
| 边界明确的局部实现、定向测试、Git/PR 收口 | GPT-5.6 Terra XHigh |
| 既有模式下的普通实现、冲突不复杂的集成 | GPT-5.6 Terra XHigh；共享核心或不确定接口再用 GPT-5.6 Terra Max |
| 安全状态、并发生命周期、跨层语义、复杂冲突、连续 CI 根因或低阶模型已失败 | GPT-5.6 Terra Ultra |
| 极复杂且影响全局的分析或 Terra 仍难以收敛的任务 | GPT-5.6 Sol Ultra |

- 所有执行会话与子代理的模型下限为已验证连通的 GPT-5.6 Luna；Luna 仅可用于固定、可重复、低风险的日志摘取、状态采样、简单文档和 Git 等机械工作，不得承担实现、定向测试、PR 收口、共享状态或需要判断的任务。不得以 GPT-5.5 或更低模型创建、恢复或续跑项目任务；Terra XHigh/Max/Ultra 继续承担实现、定向测试、PR 收口、共享状态和复杂 Windows 根因。
- 设计、实现、定向测试、Git 收口和 CI 诊断分别选择推理档位；一段复杂设计完成后，后续边界明确的实现和收口优先从 Ultra 降到 Max 或 XHigh。真正机械的固定操作可降到 Medium。
- Terra 的推理强度下限为 Medium；除真正机械任务外，通常不低于 XHigh。任务虽简单但需要细致判断时可以继续使用 Max 或 Ultra。
- Terra 不足或需要全局统筹时升级 Sol，不反复让低阶模型盲试。任务重新变得局部、确定后主动降低推理强度。
- Sol 会话的子代理可按任务使用 Sol 或 Terra；Terra 会话的子代理使用 Terra，必要时升级 Sol。
- API 中转站的容量按时段变化，某个模型与推理强度的具体组合也可能短时不可用。当前窗口失败时临时改用相邻强度、相邻模型或退避后重试，并保持上述复杂度分级；短时失败不形成永久禁用结论，后续稳定窗口重新小步探测原组合。

## 3. 渐进并发

- 初始保持 2 至 3 条活跃执行链，包括顶层会话和正在运行的嵌套子代理；只并行没有写入冲突且依赖已满足的任务。
- 连续运行稳定、没有并发上限、服务限流或共享文件冲突时，可以一次增加一条执行链；扩张后仍保留至少一条容量给 CI 故障恢复或集成。不要为了占满配额启动重复审查或低价值工作。
- 只有错误文本明确为 `agent thread limit reached` 时才按并发上限处理：停止扩张并减少活跃链路，优先让最接近交付的任务完成。HTTP 429 默认按 API 中转或上游瞬态波动处理，不自动判为并发上限、不收缩链路，也不停止健康任务；仅在另有明确资源竞争证据时再单独处置。
- 并发上限、中转站稳定性和可用模型都视为时变容量。收缩只适用于当前不稳定窗口；间隔一段时间且现有任务稳定后，再一次增加一条低冲突执行链探测恢复，不把一段时间内的反复中断外推为长期上限。
- 过期、被替代或不再对应当前基线的会话应中断，释放槽位。总调度会话应为故障恢复保留容量。
- 不让两个会话同时修改同一工作树或同一组文件。需要并行写入时使用独立分支和工作树，并明确集成顺序。

## 4. 中断与故障恢复

- 由总调度创建的会话和子代理发生中断、超时、限流或错误时，总调度自行续跑，不要求维护者再次说“继续”。
- 先检查工作树、暂存区、最新提交、远端分支、PR head 和 CI 状态，确定任务已完成到哪里，避免重复实现或覆盖已有结果。
- 状态安全时优先恢复原会话；原会话不可用时，把剩余的最小工作单元重新分发；任务只剩确定性小修改时可由总调度接管。
- 恢复后的交接必须说明继承的提交、已完成验证、剩余步骤和禁止重复的检查。
- 本项目内由总调度创建的执行会话按完整工作区权限运行，普通文件和 Git 操作不等待维护者逐项审批；破坏性操作及本文件列出的发布边界仍受限制。

## 5. 效率与验证

- 重心是做出产品。实现优先，验证与风险成比例，选择能改变决策的最小充分检查。
- 对同一 SHA 已成功的构建、合同测试、审查或 CI 不重复执行。新 SHA 只运行受改动影响的定向检查和仓库明确要求的门禁。
- 当前开发阶段以 Windows x64 成品为唯一优先架构。新功能、修复、实机验证和制品工作先完成 x64；ARM64 等 x64 功能与发行候选完整后再恢复投入。
- 已有 ARM64 源码、目录语义、构建路径和自动 CI 保持不动，不主动删除、禁用或重构。既有工作流自动产生的 ARM64 结果只作信息；不为 ARM64 专属失败重跑、修改或阻塞 x64 集成。共享改动若同时破坏 x64，按 x64 根因处理。
- 暂缓不等于 ARM64 已验收或永久取消。事项和发布证据必须把 ARM64 标为未执行或延期；原八制品发布标准在另行调整前不能用 x64 结果冒充完成。
- 窄改动优先跑 x64 定向测试；共享合同、组合根或跨模块改动再跑一次 host guardrails；Windows 本机构建和 GitHub CI 只保留会改变 x64 决策的最小检查。
- CI 失败先提取首个真实错误并定位共同根因，再修改。连续暴露同类 Windows 问题时升级模型或一次性交给 Windows 环境，不做低成本模型的盲目逐行试错。
- 已有独立审查覆盖目标风险后，不再做整 PR 泛化复核；增量修复只复核增量风险。
- macOS host 测试、GitHub Windows CI 和 Windows 11 实机验证是不同证据，记录时不得互相冒充。
- 不查询或等待与当前放行条件无关的 CI，不做没有验收用途的截图、全量审计或重复状态轮询。

### Prompt cache 友好调度

- 任务简报分为稳定前缀和单独的可变 delta 区。稳定前缀固定目标、允许文件范围、必读约束、安全边界、依赖、验收与 Git 禁令的顺序；背景以仓库文件路径和精确 SHA 引用，不重复粘贴长日志、文档或动态状态。delta 只承载本次任务所需的短期变化。
- 同一执行链的连续工作优先复用原执行会话，并在末尾追加增量 follow-up。新建且相互独立的任务默认使用 `fork_turns=none`，或仅传入满足交付所需的最小有界历史；无论是否复用历史，安全、依赖和验收约束都必须完整保留。
- 固定任务分发中的工具调用顺序、任务顺序和交接字段。commit SHA、PR/CI 状态、完成进度、第一真实错误及维护者决定一律置于 delta 末尾，避免扰动稳定前缀；交接只记录继承提交、已验证项、剩余步骤和禁止重复的检查。
- 仅在服务已暴露 `cache-read` 或 `cache-hit` 趋势时进行低成本观察。不得为了测量缓存重跑构建、测试或任务，不得臆造缓存率，也不得将 API 提示缓存行为表述为 Codex 客户端命中保证。
- 缓存优化只减少重复上下文，不改变调度边界：独立 worktree、Git 安全、Windows x64 优先、最小充分验证和执行会话/子代理最低 GPT-5.6 Luna 的既有规范均不得削弱。

OpenAI 的 prompt caching 资料说明缓存按请求起始前缀匹配，因此稳定说明与工具定义应置前、可变状态置后，工具定义及其顺序应保持稳定，连续交接应追加在末尾。本节据此优化任务组织；实际命中仍取决于服务和客户端行为。

## 6. Git 与 GitHub 节奏

- 一个内聚工作单元完成并通过最小门禁后就提交；达到可共享、可恢复的进度时推送远端，不把所有工作积到最后。
- 功能分支及时创建 Draft PR。达到准确 head、必要 CI 和风险复核后再转 Ready，并按既定依赖顺序集成。
- 多功能集成使用普通 merge 把最新 integration 带入 feature 分支，解决冲突并验证新的 feature head；禁止 rebase、force push 和历史改写。
- 默认集成目标是 `codex/v1-integration`。未经维护者明确要求，不合入 `main`，不创建 tag 或 GitHub Release，不接受 WiX 条款。
- 保护维护者的未提交和未跟踪内容。不得删除、重置或顺带提交无关文件；主工作树不适合写入时使用独立 worktree。
- 提交和 PR 证据绑定精确 SHA、CI run 和实际执行环境；事项 Markdown 在相应实现已集成且证据成立后收口。

## 7. Windows 原生主执行环境

- Windows 工作区路径、代理产物、创建/迁移/清理和证据边界必须遵循 `docs/agents/windows-workspace-path-policy.md`；该文档对 `D:\azzs`、`D:\azzs-codex`、根目录禁写、盘符映射禁用和既有用户路径保护具有约束力。
- 从 2026-08-13 起，新的总调度和后续执行默认在维护者的 Windows 11 25H2 原生环境进行；GitHub 是跨会话状态的权威中转，不再把 macOS 或虚拟机作为日常执行端。
- Windows 总调度从 `origin/codex/v1-integration` 克隆或更新，先阅读 `docs/agents/windows-native-takeover.md`，再使用独立 worktree 分发任务。执行会话直接完成实现、x64 最小验证、提交、推送、PR 和集成，不把普通操作交回维护者。
- 减少人工 UI 验收。只有结果会改变 x64 发布决策且无法由无界面合同或自动化替代时才请求维护者操作；相邻 UAC、Explorer、安装器和 UIA 场景集中到同一个接近发行候选的验收批次。
- 旧 macOS/虚拟机观察只按已记录的证据等级保留，不重复采集，不外推为 Windows 原生通过。未形成可信证据的场景保持未验证，先推进依赖链上的产品实现。
- 主执行环境变化不扩大发布权限：仍不得未经明确授权合入 `main`、创建 tag/GitHub Release 或接受 WiX 条款。

## 8. 分发模板

每个执行任务至少明确：

1. 目标结果和对应事项/规格。
2. 起始分支、精确 SHA、工作树及允许修改的文件范围。
3. 依赖、集成顺序和不能覆盖的既有成果。
4. 必读的 `AGENTS.md`、工程文档与适用技能。
5. 验收条件和唯一必要的验证命令。
6. 提交、推送、Draft/Ready PR 规则及禁止操作。
7. 完成回报：最终 SHA、改动摘要、已运行验证、未验证边界、PR/CI 链接和剩余阻断。

任务完成的判断是成果已实现、可恢复地进入 Git/GitHub、证据准确且下一依赖可以继续，不是产生了更多计划或核验记录。
